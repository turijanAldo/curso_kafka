problema de resiliencia

1.2 — Crear el topic pedidos-tiendamax

⚠️ FIX APLICADO — Kafka 4.x en apache/kafka:4.2.0
La imagen apache/kafka:4.2.0 no agrega /opt/kafka/bin al PATH por defecto. Todas las herramientas CLI (kafka-topics.sh, kafka-console-producer.sh, etc.) están en /opt/kafka/bin/. Siempre que entres al container, ejecuta primero: 
export PATH=/opt/kafka/bin:$PATH
O usa la ruta completa: /opt/kafka/bin/kafka-topics.sh
bash · dentro del container
COMANDO
¿POR QUÉ?
kafka-topics.sh --create
Crea el canal por donde fluirán los pedidos. En Kafka, el topic es la abstracción lógica — las particiones son la implementación física.
--topic pedidos-tiendamax
CONVENCIÓN Nombre descriptivo con dominio + evento. En producción: v1.pedidos.creados. El prefijo de versión permite migración sin downtime.
--partitions 3
DECISIÓN CRÍTICA 3 particiones = máximo 3 consumers en paralelo. Elegimos 3 porque tenemos exactamente 3 servicios (inventario, notif., factura.). Más consumers = standby.
--replication-factor 1
DEV ONLY En local solo tenemos 1 broker → RF=1. En producción mínimo RF=3 para tolerar la caída de 1 broker sin pérdida de datos. (Módulo 2 → ISR)
--config retention.ms=604800000
604800000 ms = 7 días. Si el servicio de inventario cae y tarda 3 días en recuperarse, no pierde ningún pedido — los mensajes siguen en Kafka esperando.
--bootstrap-server localhost:9092
El cliente contacta a este broker primero para obtener los metadatos del clúster (quién es líder de cada partición). No es el único broker, es el punto de entrada.

1.3 — Fix de flags deprecados en Kafka 4.x

🔧 KAFKA 4.x — CAMBIO DE FLAGS EN CLI

En Kafka 4.x, los flags del console-producer y consumer fueron separados. Usar --property lanza un Warning y puede fallar silenciosamente:

HERRAMIENTAFLAG VIEJO ❌FLAG CORRECTO KAFKA 4.x ✅
console-producer--property parse.key=true--reader-property parse.key=true
console-producer--property key.separator=:--reader-property key.separator=:
console-consumer--property print.key=true--formatter-property print.key=true
console-consumer--timeout-ms 5000 (poco confiable)--max-messages N (termina al leer N mensajes)

¿Por qué este split? Kafka 4.x separó la lógica de lectura del stdin (reader) de la lógica de formateo del output (formatter) para mayor claridad y extensibilidad.

Comandos corregidos para Kafka 4.2.0:

Producer — enviar con key 
# Dentro del container (con PATH ya configurado)
kafka-console-producer.sh \
  --topic pedidos-tiendamax \
  --bootstrap-server localhost:9092 \
  --reader-property parse.key=true \   # ← correcto en Kafka 4.x
  --reader-property key.separator=:    # ← formato: ORD-001:{json}

# Escribe y presiona Enter:
ORD-001:{"order_id":"ORD-001","cliente":"ana","total":299}
ORD-002:{"order_id":"ORD-002","cliente":"bob","total":149}
ORD-003:{"order_id":"ORD-003","cliente":"ana","total":89}
Consumer — leer desde el inicio 
kafka-console-consumer.sh \
  --topic pedidos-tiendamax \
  --from-beginning \               # ← auto.offset.reset=earliest
  --max-messages 10 \              # ← termina después de 10 mensajes (más confiable que --timeout-ms)
  --formatter-property print.key=true \
  --formatter-property key.separator=" → " \
  --bootstrap-server localhost:9092
✅ OUTPUT ESPERADO DEL CONSUMER
ORD-001 → {"order_id":"ORD-001","cliente":"ana","total":299}
ORD-002 → {"order_id":"ORD-002","cliente":"bob","total":149}
ORD-003 → {"order_id":"ORD-003","cliente":"ana","total":89}
Processed a total of 3 messages

Observa que ORD-001 y ORD-003 son del mismo cliente "ana" — con key=ORD-001 y key=ORD-003 van a diferentes particiones (el key es el order_id, no el cliente). Esto garantiza que los pedidos de cualquier orden específica se procesen en orden, independientemente del cliente.

💡 ¿POR QUÉ LA KEY ES order_id Y NO cliente_id?
  • Orden garantizado por pedido: todos los eventos de ORD-001 (creado → pagado → enviado → entregado) van a la misma partición → en secuencia
  • Evita hotspot: si usáramos cliente_id y "ana" hace 80% de los pedidos, una partición se saturaría
  • Si usáramos sin key: Round Robin distribuye bien la carga pero pierde el orden — el evento "enviado" podría llegar antes que "pagado"

2.4 — PedidoProducer.java — el corazón de este paso

PedidoProducer.java · anotado línea a línea
CÓDIGO
¿POR QUÉ ESTÁ ESO AHÍ?
props.put("bootstrap.servers",
"localhost:9092");
Punto de entrada al clúster. El producer contacta este broker para obtener metadatos (quién es líder de cada partición). En producción serían 3+ brokers separados por coma.
props.put("acks", "all");
CRÍTICO El producer espera ACK del líder Y todas las réplicas ISR antes de considerar el mensaje enviado. Si el broker cae justo después del send, el mensaje no se pierde. Conecta con lo que viste en el Módulo 3 y el Simulador.
props.put("enable.idempotence", "true");
POR QUÉ Si la red falla y el producer reintenta, Kafka detecta el duplicado (PID + sequence number) y descarta el segundo. Sin esto, un pedido podría procesarse dos veces. Módulo 3 → PID/idempotencia.
props.put("retries", "3");
Reintentos automáticos si el broker no responde. Con enable.idempotence=true los reintentos son seguros — Kafka deduplica. Sin idempotencia, reintentar = duplicados.
props.put("key.serializer",
"...StringSerializer");
Kafka transporta byte[]. Este serializer convierte el String key ("ORD-001") a bytes. El broker aplica murmur2(key) % numPartitions a esos bytes para determinar la partición.
props.put("value.serializer",
"...StringSerializer");
Enviamos el Pedido como JSON String. En producción se usa Avro + Schema Registry para validar el esquema en tiempo real. Por ahora JSON es suficiente para el lab.
new ProducerRecord<>(
TOPIC, orderId, jsonPedido)
CLAVE DEL DISEÑO El segundo argumento es la key = orderId. Esto garantiza que todos los eventos del mismo pedido (CREADO→PAGADO→ENVIADO) siempre van a la misma partición → orden garantizado.
producer.send(record,
(metadata, ex) -> { ... })
El callback de confirmación. Si ex == null: éxito, muestra partición + offset. Si ex != null: fallo, loguea el error. Esto es lo que hace at-least-once — confirmas antes de avanzar.
metadata.partition()
metadata.offset()
El broker confirma exactamente en qué partición y en qué offset quedó el mensaje. Puedes guardar esto en tu DB para hacer exactly-once a nivel de aplicación (verificar idempotencia del negocio).
producer.flush();
producer.close();
flush() bloquea hasta que todos los mensajes pendientes en el buffer se enviaron y recibieron ACK. close() libera las conexiones. Sin flush() podrías perder mensajes al cerrar.

Código completo — listo para copiar y ejecutar:

src/main/java/com/tiendamax/PedidoProducer.java 
package com.tiendamax;

import com.fasterxml.jackson.databind.ObjectMapper;
import com.tiendamax.model.Pedido;
import org.apache.kafka.clients.producer.*;
import org.apache.kafka.common.serialization.StringSerializer;
import java.util.Properties;

public class PedidoProducer {

    private static final String TOPIC    = "pedidos-tiendamax";
    private static final String BROKER   = "localhost:9092";
    private static final ObjectMapper MAPPER = new ObjectMapper();

    public static void main(String[] args) throws Exception {

        // ── 1. Configuración del producer ──────────────────
        Properties props = new Properties();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG,  BROKER);
        props.put(ProducerConfig.ACKS_CONFIG,               "all");       // espera todas las ISR
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, "true");    // sin duplicados en retry
        props.put(ProducerConfig.RETRIES_CONFIG,            3);
        props.put(ProducerConfig.LINGER_MS_CONFIG,          5);            // batching: espera 5ms
        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG,
                  StringSerializer.class.getName());
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG,
                  StringSerializer.class.getName());

        // ── 2. Pedidos de muestra para el lab ──────────────
        Pedido[] pedidos = {
            new Pedido("ORD-001", "cli-ana",  "Laptop",  1299.00),
            new Pedido("ORD-002", "cli-bob",  "Teclado",   89.00),
            new Pedido("ORD-003", "cli-ana",  "Mouse",     45.00),
            new Pedido("ORD-004", "cli-carlos","Monitor", 399.00),
            new Pedido("ORD-005", "cli-bob",  "Webcam",   129.00),
            new Pedido("ORD-006", "cli-diana","Audífonos", 79.00),
            new Pedido("ORD-007", "cli-ana",  "SSD 1TB",  159.00),
            new Pedido("ORD-008", "cli-carlos","RAM 32GB", 89.00),
            new Pedido("ORD-009", "cli-diana","Mousepad",  19.00),
            new Pedido("ORD-010", "cli-bob",  "Hub USB",   35.00),
        };

        // ── 3. Enviar cada pedido ───────────────────────────
        try (KafkaProducer<String, String> producer =
                new KafkaProducer<>(props)) {

            for (Pedido pedido : pedidos) {
                String jsonValue = MAPPER.writeValueAsString(pedido);

                // KEY = orderId → misma partición para todos los eventos del pedido
                ProducerRecord<String, String> record =
                    new ProducerRecord<>(TOPIC, pedido.getOrderId(), jsonValue);

                producer.send(record, (metadata, ex) -> {
                    if (ex == null) {
                        System.out.printf(
                            "✅ Enviado: %s → P-%d offset=%d%n",
                            pedido.getOrderId(),
                            metadata.partition(),
                            metadata.offset());
                    } else {
                        System.err.println("❌ Error enviando "
                            + pedido.getOrderId() + ": " + ex.getMessage());
                    }
                });

                Thread.sleep(200); // pausa para ver el log ordenado
            }

            producer.flush(); // espera ACK de todos antes de cerrar
            System.out.println("\n📊 Todos los pedidos enviados. Verifica distribución:");
            System.out.println("  kafka-consumer-groups.sh --describe (Paso 6)");
        }
    }
}

PASO 3 🔴 EN CURSO
CONSUMER CON COMMIT MANUAL

PedidoConsumer.java

El consumer lee pedidos del topic, los procesa (inventario / notificaciones / factura) y confirma el offset solo después de procesar — garantizando semántica at-least-once.

TIMING DEL COMMIT → SEMÁNTICA DE ENTREGA
  POLL → PROCESO → COMMIT          ← at-least-once ✅ (crash antes del commit → relee)
  POLL → COMMIT → PROCESO            ← at-most-once  ⚠️  (crash antes de procesar → mensaje perdido)
  POLL → PROCESO → DB + COMMIT (atómico) ← exactly-once  🏆 (requiere transacciones Kafka)
→ Nosotros usamos at-least-once: commitSync() va al final del loop, después de procesar todos los registros del poll batch.

⚙️ CONFIGURACIÓN DEL KAFKACONSUMER — línea por línea

Código¿Por qué?
GROUP_ID = "grupo-tiendamax" Todos los consumers con el mismo ID forman un Consumer Group. Kafka distribuye las particiones entre ellos. Cambia el ID → grupo independiente que lee TODO el topic desde el principio.
AUTO_OFFSET_RESET = "earliest" Si no hay offset guardado para este grupo (primera vez, o después de un reset), lee desde el offset 0. Con latest ignoraría todos los mensajes anteriores.
ENABLE_AUTO_COMMIT = "false" Con auto-commit=true Kafka commitea cada N segundos sin importar si procesaste bien el mensaje. Un crash entre el auto-commit y el procesamiento real → mensaje perdido silenciosamente. Lo desactivamos para controlar nosotros cuándo commitear.
MAX_POLL_RECORDS = 10 Máximo de mensajes por poll(). Con 10 pedidos de prueba, vemos todo en un solo poll. En producción, ajusta según la capacidad de tu pipeline de procesamiento.
HEARTBEAT_INTERVAL_MS = 3000 Cada 3 segundos el consumer avisa al Group Coordinator que sigue vivo. Si no llega heartbeat en session.timeout.ms → rebalanceo: Kafka redistribuye las particiones entre los consumers restantes.
SESSION_TIMEOUT_MS = 10000 Si Kafka no recibe heartbeat en 10 seg → consumer muerto. Regla: heartbeat < session_timeout / 3. Con 3000 ms de heartbeat y 10000 ms de session timeout hay margen para 3 heartbeats fallidos antes del rebalanceo.
consumer.subscribe(List.of(TOPIC)) En lugar de assign() manual, subscribe() permite el rebalanceo automático: cuando se une un nuevo consumer o cae uno, Kafka redistribuye las particiones sin intervención manual.
consumer.poll(Duration.ofMillis(1000)) Bloquea hasta 1 segundo esperando mensajes. El SDK envía heartbeats internamente durante el poll. Si tu procesamiento tarda más que max.poll.interval.ms (default 5 min) → Kafka asume que el consumer murió → rebalanceo.
consumer.commitSync() Commit síncrono (bloquea hasta que el broker confirma en __consumer_offsets). Va al final del loop, después de procesar todos los records del poll batch. Si el proceso cae antes → relee. Si cae después → ya está commiteado.
mainThread.interrupt() Shutdown hook: captura Ctrl+C y interrumpe el hilo principal. El loop while (!Thread.currentThread().isInterrupted()) detecta la interrupción y termina limpiamente — el try-with-resources cierra el consumer y envía el último heartbeat al grupo.

📄 PedidoConsumer.java — código completo

src/main/java/com/tiendamax/PedidoConsumer.java 
package com.tiendamax;

import com.fasterxml.jackson.databind.ObjectMapper;
import com.tiendamax.model.Pedido;
import org.apache.kafka.clients.consumer.ConsumerConfig;
import org.apache.kafka.clients.consumer.ConsumerRecord;
import org.apache.kafka.clients.consumer.ConsumerRecords;
import org.apache.kafka.clients.consumer.KafkaConsumer;
import org.apache.kafka.common.serialization.StringDeserializer;
import java.time.Duration;
import java.util.List;
import java.util.Properties;

public class PedidoConsumer {

    // ── 1. Constantes ─────────────────────────────────────────────────
    private static final String TOPIC    = "pedidos-tiendamax";
    private static final String BROKER   = "localhost:9092";
    private static final String GROUP_ID = "grupo-tiendamax";
    private static final ObjectMapper MAPPER = new ObjectMapper(); // thread-safe

    public static void main(String[] args) throws Exception {
        String servicio = args.length > 0 ? args[0] : "generico";

        // ── 2. Configuración del KafkaConsumer ────────────────────────
        Properties props = new Properties();
        props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG,   BROKER);
        props.put(ConsumerConfig.GROUP_ID_CONFIG,            GROUP_ID);
        props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG,   "earliest");
        props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG,  "false");  // ← CRÍTICO
        props.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG,    10);
        props.put(ConsumerConfig.HEARTBEAT_INTERVAL_MS_CONFIG, 3000);
        props.put(ConsumerConfig.SESSION_TIMEOUT_MS_CONFIG,    10000);
        props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG,
                  StringDeserializer.class.getName());
        props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG,
                  StringDeserializer.class.getName());

        // ── 3. Shutdown hook — cierre limpio con Ctrl+C ───────────────
        Thread mainThread = Thread.currentThread();
        Runtime.getRuntime().addShutdownHook(new Thread(() -> {
            System.out.printf("\n[%s] 🛑 Señal de cierre recibida...%n", servicio);
            mainThread.interrupt();
        }));

        // ── 4. Poll loop ──────────────────────────────────────────────
        try (KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props)) {

            consumer.subscribe(List.of(TOPIC));   // → rebalanceo automático
            System.out.printf("[%s] 👂 Escuchando '%s' en grupo '%s'...%n",
                servicio, TOPIC, GROUP_ID);

            while (!Thread.currentThread().isInterrupted()) {

                ConsumerRecords<String, String> records =
                    consumer.poll(Duration.ofMillis(1000));

                if (records.isEmpty()) {
                    System.out.printf("[%s] ⏳ Esperando mensajes...%n", servicio);
                    continue;
                }

                System.out.printf("[%s] 📦 Recibidos %d mensajes:%n",
                    servicio, records.count());

                // Procesar cada record del poll batch
                for (ConsumerRecord<String, String> record : records) {
                    try {
                        Pedido pedido = MAPPER.readValue(record.value(), Pedido.class);
                        procesarPedido(servicio, pedido, record);
                    } catch (Exception e) {
                        System.err.printf("[%s] ❌ Error offset=%d: %s%n",
                            servicio, record.offset(), e.getMessage());
                        // En prod: dead-letter topic, retry, alertas
                    }
                }

                // at-least-once: commit DESPUÉS de procesar todos los records
                consumer.commitSync();
                System.out.printf("[%s] ✔  Commit realizado.%n%n", servicio);
            }

        } catch (Exception e) {
            if (!Thread.currentThread().isInterrupted())
                System.err.println("Error inesperado: " + e.getMessage());
        }
        System.out.printf("[%s] 👋 Consumer cerrado limpiamente.%n", servicio);
    }

    // ── Simula el trabajo del microservicio ───────────────────────────
    // Método privado → SRP: separa lógica de negocio de infraestructura Kafka
    private static void procesarPedido(String servicio, Pedido pedido,
                                          ConsumerRecord<String, String> record)
                                          throws InterruptedException {
        Thread.sleep(50 + (long)(Math.random() * 100));  // simula latencia

        String accion = switch (servicio) {
            case "inventario"     -> "📦 Reservando stock: " + pedido.getProducto();
            case "notificaciones" -> "📧 Email a: "          + pedido.getClienteId();
            case "facturacion"    -> "🧾 Factura: $"         + pedido.getTotal();
            default             -> "⚙️  Procesando: "       + pedido.getOrderId();
        };

        System.out.printf("  [%s] %s  |  P-%d offset=%-3d  key=%s%n",
            servicio, accion, record.partition(), record.offset(), record.key());
    }
}

💡 ¿POR QUÉ commitSync() Y NO commitAsync()?
commitAsync() no bloquea (mejor throughput) pero si falla, no reintenta — un commit fallido puede dejar el offset atrás y causar reprocesamiento. commitSync() reintenta automáticamente hasta conseguir confirmación del broker o fallar definitivamente.

Patrón híbrido en producción: usar commitAsync() en cada iteración del loop para throughput, y commitSync() en el bloque finally para garantizar el último commit antes de cerrar.

ALGORITMO DE ASIGNACIÓN — ejecutado por el Group Coordinator al hacer el rebalanceo
RangeAssignor · pedidos-tiendamax · 3 particiones · 3 consumers 
Paso 1 — ordenar particiones del topic:
    [P0, P1, P2]

Paso 2 — ordenar consumers del grupo (por member-id):
    [consumer-inventario-xxx, consumer-notificaciones-yyy, consumer-facturacion-zzz]

Paso 3 — dividir:
    n = floor(3 particiones / 3 consumers) = 1  por consumer
    r = 3 % 3 = 0  (sin resto → distribución exacta, nadie recibe extra)

Resultado:
    consumer-inventario    → [P0]
    consumer-notificaciones → [P1]
    consumer-facturacion   → [P2]
💡 Regla de oro: con N particiones y N consumers en el mismo grupo → distribución perfecta, 1 partición por consumer. Si hay más consumers que particiones, los sobrantes quedan idle (en espera como backup). Si hay menos consumers, algunos reciben 2 o más particiones.

PASO 5 🔴 EN CURSO
TOLERANCIA A FALLOS · REBALANCEO · AT-LEAST-ONCE EN ACCIÓN

Simulación de fallo y rebalanceo

Con los 3 consumers corriendo del Paso 4, matamos uno con Ctrl+C. Kafka detecta el silencio, dispara un rebalanceo y el Group Coordinator redistribuye automáticamente la partición huérfana entre los consumers supervivientes — sin intervención manual.

⚡ DOS TIPOS DE FALLO — cómo los detecta Kafka

CIERRE LIMPIO — Ctrl+C
El shutdown hook (línea del addShutdownHook) interrumpe el hilo principal. El consumer llama a close() → notifica al Group Coordinator en ese instante.

⏱ Rebalanceo: inmediato — sin esperar timeout.
CRASH — proceso muerto / OOM / kill -9
El proceso muere sin avisar. El broker espera session.timeout.ms sin recibir heartbeat. Pasados los 10 segundos (nuestro config), el Group Coordinator declara al consumer muerto.

⏱ Rebalanceo: ~10 seg después del crash.

⚡ AT-LEAST-ONCE EN ACCIÓN — reprocesamiento tras el fallo
Si notificaciones había procesado mensajes de P1 pero aún no había llamado a commitSync() (crash en medio del loop), esos offsets no están commiteados en __consumer_offsets.

Cuando inventario asume P1, lee desde el último committed offset → esos mensajes se procesan de nuevo. Resultado: at-least-once — posible duplicado, pero ningún mensaje se pierde.

En producción se maneja con idempotencia en el destino (DB upsert, deduplicación por orderId).

PASO 6 🔴 EN CURSO
OBSERVABILIDAD · CONSUMER LAG · RESET DE OFFSETS

Monitoreo de lag y reset de offsets

El consumer lag es la métrica más importante en Kafka: cuántos mensajes tiene pendientes tu grupo. Un lag creciente significa que el consumer no procesa tan rápido como el producer produce — la primera señal de alarma en producción. También veremos cómo resetear offsets para reprocesar todo el historial o saltar mensajes problemáticos.

📐 ¿QUÉ ES EL CONSUMER LAG?

concepto · lag por partición 
  Partición P0  →  offsets almacenados en el log del broker:

  ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐

  │ORD-1 │ORD-4 │ORD-8 │ORD-10│ORD-11│ORD-12│ORD-13│ORD-14│
  └──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘
                                  ▲                         ▲
                          COMMITTED-OFFSET = 4    LOG-END-OFFSET = 8

  LAG = LOG-END-OFFSET − COMMITTED-OFFSET = 8 − 4 = 4

  ← los 4 mensajes entre ambos punteros están sin leer (o sin commitear)

🗂️ COLUMNAS DE --describe — qué significa cada una

ColumnaSignificadoEjemplo
GROUP Nombre del Consumer Group. Un mismo topic puede tener múltiples grupos leyendo de forma independiente. grupo-tiendamax
TOPIC Nombre del topic que está consumiendo este grupo. pedidos-tiendamax
PARTITION Número de partición. Una fila por cada partición del topic. 0, 1, 2
CURRENT-OFFSET El último offset que el grupo commiteó en __consumer_offsets. Desde aquí reanudará si reinicia. 4
LOG-END-OFFSET El último offset que existe en el log del broker (el mensaje más reciente escrito). 8
LAG LOG-END-OFFSET − CURRENT-OFFSET. La métrica más crítica: cuántos mensajes están pendientes de procesar. LAG=0 es el objetivo. 4 → alerta
CONSUMER-ID ID único del consumer al que está asignada esa partición. Vacío si el grupo está inactivo (ningún consumer corriendo). inventario-abc123

🔁 RESET DE OFFSETS — volver a procesar mensajes

⚠️ Prerequisito: El Consumer Group debe estar inactivo (sin ningún consumer corriendo). Si hay consumers activos, el reset falla con error. Para esto el grupo ya estaba parado en el experimento anterior.
Opción¿Qué hace?Cuándo usarlo
--to-earliest Mueve el committed-offset al offset 0 de cada partición. Al relanzar el consumer, reprocesa todos los mensajes del topic. Reprocessing completo: nuevo campo en DB, bug fix que requiere recalcular todo.
--to-latest Mueve el offset al final del log. El consumer ignora todos los mensajes existentes y solo lee los nuevos. Saltar mensajes envenenados o un backlog antiguo irrelevante.
--to-offset N Mueve el offset exactamente a N en la partición especificada. Replay quirúrgico: "quiero reprocesar desde el mensaje 150 de P0".
--shift-by -N Retrocede N posiciones desde el committed-offset actual. Reprocesar solo los últimos N mensajes sin saber el offset exacto.
--by-duration PT1H Retrocede hasta el mensaje más antiguo dentro de la última hora (formato ISO 8601). Reprocesar el último bloque de tiempo tras un incidente en producción.
