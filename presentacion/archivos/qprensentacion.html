¿Qué es Apache Kafka?

Plataforma distribuida de streaming de eventos de código abierto

Alto Rendimiento

Millones de mensajes por segundo con latencia de milisegundos

Durabilidad

Persistencia en disco con replicación y tolerancia a fallos

Conceptos Clave:
  • Topics: Categorías de mensajes (ej: transacciones, logs, auditoría)
  • Partitions: Dividen topics para paralelismo y escalabilidad
  • Brokers: Nodos del cluster que almacenan y sirven datos
  • Consumer Groups: Múltiples consumidores procesando en paralelo

Arquitectura de Kafka

Componentes fundamentales para entender su funcionamiento

Productores (Producers)

Aplicaciones que publican eventos a topics de Kafka.

// Ejemplo: Publicar transacción financiera const producer = new KafkaProducer({ bootstrapServers: 'kafka.fintech.local:9092', acks: 'all' // Garantizar persistencia }); await producer.send({ topic: 'transactions', messages: [{ key: 'tx_12345', value: JSON.stringify({ amount: 1500.00, currency: 'USD', timestamp: new Date().toISOString() }) }] });
Consumidores (Consumers)

Aplicaciones que suscriben y procesan eventos de topics.

// Ejemplo: Procesar transacciones en tiempo real const consumer = new KafkaConsumer({ groupId: 'fraud-detection-service', autoOffsetReset: 'earliest' }); await consumer.subscribe({ topic: 'transactions' }); await consumer.run({ eachMessage: async ({ message }) => { const tx = JSON.parse(message.value); await fraudAnalyzer.check(tx); // Lógica de negocio } });
Broker & Persistencia
  • Logs segmentados en disco para alto throughput
  • Replicación entre brokers para alta disponibilidad
  • Retención configurable (horas a años)
  • ZooKeeper/KRaft para coordinación del cluster
  • Balanceo automático de particiones
  • SSL/SASL para seguridad empresarial

Ventajas Clave
  • Desacoplamiento temporal: Servicios no necesitan estar disponibles simultáneamente
  • Escalabilidad independiente: Cada servicio escala según su carga
  • Resiliencia: Buffer de mensajes ante caídas de consumidores
  • Replay de eventos: Reprocesar datos para debugging o nuevos features
Patrones Comunes
  • Event Sourcing: Estado derivado de secuencia de eventos inmutables
  • CQRS: Separación de lecturas y escrituras con proyecciones
  • Saga Pattern: Coordinación de transacciones distribuidas
  • Change Data Capture: Replicar cambios de BD a otros servicios
Ejemplo: Saga de Transferencia Bancaria
// Paso 1: Iniciar transferencia await kafka.send({ topic: 'transfer.initiated', messages: [{ key: txId, value: JSON.stringify(payload) }] }); // Servicio de Débito (escucha 'transfer.initiated') // → Publica 'debit.completed' o 'debit.failed' // Servicio de Crédito (escucha 'debit.completed') // → Publica 'credit.completed' // Servicio de Notificación (escucha eventos finales) // → Envía confirmación al cliente // Compensación: Si falla crédito, se publica 'credit.failed' // → Servicio de Débito escucha y ejecuta reversa

Configuración Recomendada para Logs
  • Compresión: compression.type=zstd para ahorrar almacenamiento
  • Retención: retention.ms=604800000 (7 días) en caliente + cold storage
  • Particiones: Basadas en service_name para paralelismo
  • Schema: Avro/Protobuf con Schema Registry para evolución segura
Casos de Uso en Observabilidad
🔍 Debugging Distribuido

Correlacionar logs de múltiples servicios usando trace_id como key de Kafka.

📊 Métricas en Tiempo Real

Agregación de logs para dashboards de latencia, errores y throughput.

🚨 Alertas Inteligentes

Detección de anomalías con streams de Kafka + ksqlDB o Flink.

🔐 Seguridad & Auditoría

Pipeline inmutable para logs de acceso, autenticación y cambios críticos.

// Ejemplo: Enriquecer logs antes de almacenar ksqlDB CREATE STREAM enriched_logs AS SELECT original.*, geo_lookup(ip) AS location, user_risk_score(user_id) AS risk FROM raw_logs EMIT CHANGES;

Mejores Prácticas y Conclusión

Recomendaciones para implementar Kafka en producción

Do's
  • Usar acks=all para datos financieros críticos
  • Implementar Schema Registry para evolución de contratos
  • Monitorear consumer lag como métrica de salud
  • Aplicar rate limiting en productores para evitar sobrecarga
  • Usar topics separados por dominio y criticidad
  • Planificar capacidad con margen para picos (Black Friday, etc.)
Don'ts
  • ❌ No usar Kafka como cola de tareas de larga duración
  • ❌ No almacenar datos sensibles sin encriptación en tránsito/reposo
  • ❌ No ignorar el backpressure en consumidores lentos
  • ❌ No mezclar eventos de diferente criticidad en el mismo topic
  • ❌ No olvidar pruebas de recuperación ante desastres
  • ❌ No subestimar la complejidad operativa: considerar Confluent Cloud o managed services
