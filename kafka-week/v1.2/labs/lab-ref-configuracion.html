docker-compose.yml — Linea por Linea

El archivo configura un nodo Kafka 4.2.0 en modo KRaft (sin ZooKeeper). Usa las pestanas para explorar cada grupo de propiedades.

image
apache/kafka:4.2.0
Imagen oficial de Apache Kafka. La version 4.x soporta KRaft de forma nativa sin necesidad de ZooKeeper. No usamos Confluent ni Bitnami.
container_name
kafka
Nombre fijo del contenedor. Permite usar docker exec kafka ... directamente en los comandos del curso.
ports
"9092:9092"
Mapea el puerto 9092 del contenedor al host. Los producers/consumers Java se conectan a localhost:9092. El puerto 9093 (controller) NO se expone: solo es para comunicacion interna de KRaft.
KAFKA_NODE_ID
1
Identificador unico del nodo en el cluster. En produccion, cada nodo tiene un ID distinto (1, 2, 3...). Con un solo nodo de desarrollo usamos 1.
KAFKA_PROCESS_ROLES
broker,controller
Modo combinado KRaft. Este nodo actua como broker (recibe mensajes) Y como controller (gestiona metadata del cluster). En produccion se separan en nodos distintos para mayor resiliencia.
CLUSTER_ID
"MkU3OEVBNTcwNTJENDM2Qk"
UUID unico del cluster KRaft. Se genera con kafka-storage.sh random-uuid. Todos los nodos del mismo cluster deben compartir este ID. Reemplaza el antiguo ZooKeeper como fuente de identidad del cluster.
KAFKA_LISTENERS
PLAINTEXT://:9092, CONTROLLER://:9093
Define en que interfaces/puertos escucha el broker. PLAINTEXT (9092) para producers y consumers. CONTROLLER (9093) exclusivamente para el protocolo KRaft entre controllers.
KAFKA_ADVERTISED_LISTENERS
PLAINTEXT://localhost:9092
Direccion que el broker anuncia a los clientes. Los producers/consumers usan esta direccion para conectarse. Usamos localhost porque todo corre en la misma maquina.
KAFKA_LISTENER_SECURITY_PROTOCOL_MAP
PLAINTEXT:PLAINTEXT, CONTROLLER:PLAINTEXT
Mapea cada listener a un protocolo de seguridad. Ambos usan PLAINTEXT (sin TLS) para desarrollo. En produccion usarias SSL o SASL_SSL.
KAFKA_CONTROLLER_LISTENER_NAMES
CONTROLLER
Indica cual listener se usa para comunicacion entre controllers KRaft. Debe coincidir con uno de los nombres definidos en KAFKA_LISTENERS.
KAFKA_CONTROLLER_QUORUM_VOTERS
1@kafka:9093
Lista de controllers que forman el quorum. Formato: nodeId@host:port. Con un solo nodo, el quorum se forma consigo mismo. En produccion con 3 controllers: 1@kafka1:9093,2@kafka2:9093,3@kafka3:9093.
KAFKA_LOG_DIRS
/var/lib/kafka/data
Directorio donde Kafka persiste los datos de los topics (segmentos de log). Se monta como volumen Docker para sobrevivir reinicios del contenedor.
KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR
1
Factor de replicacion del topic interno __consumer_offsets. Con 1 broker solo se puede tener factor 1. En produccion con 3+ brokers, usar 3.
KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR
1
Factor de replicacion del topic interno de transacciones. Mismo razonamiento: 1 broker = factor 1.
KAFKA_TRANSACTION_STATE_LOG_MIN_ISR
1
Minimo de replicas in-sync requeridas para escribir en el log de transacciones. Con factor 1, el ISR minimo debe ser 1.
volumes
kafka-data:/var/lib/kafka/data
Volumen nombrado de Docker. Los datos de los topics persisten aunque hagas docker compose down. Para limpiar: docker compose down -v (elimina volumenes).
healthcheck.test
kafka-topics.sh --list
Verifica que el broker esta operativo intentando listar topics. Si falla, Docker marca el contenedor como unhealthy.
healthcheck.start_period
30s
Kafka tarda ~20-30s en arrancar. Durante este periodo, los fallos del healthcheck no cuentan. Evita que Docker reinicie el contenedor mientras Kafka todavia esta arrancando.

pom.xml — Dependencias Maven

El proyecto usa solo 3 dependencias, sin Spring ni frameworks pesados. Java 17 como target.

kafka-clients 3.7.1
Cliente Java oficial de Apache Kafka. Incluye KafkaProducer, KafkaConsumer, ProducerRecord, ConsumerRecord, serializadores y toda la API de bajo nivel. No es Kafka Streams ni Confluent: es el cliente puro sin abstracciones adicionales.
jackson-databind 2.17.1
Serializa objetos Java a JSON y viceversa. El ObjectMapper convierte Pedido a String (JSON) antes de enviarlo a Kafka, y lo reconstruye en el consumer. Usa anotaciones como @JsonProperty para mapear nombres de campos.
slf4j-simple 2.0.13
Logger minimo para que kafka-clients pueda escribir logs internos en la consola. Sin esta dependencia, los logs de Kafka se pierden o generan warnings en stderr.
exec-maven-plugin 3.1.0: Permite ejecutar clases Java directamente con mvn exec:java -Dexec.mainClass="com.tiendamax.XYZ" sin necesidad de crear un JAR.

Pedido.java — Modelo de Datos

El modelo POJO que se serializa a JSON y viaja como VALUE del mensaje Kafka.

Pedido.java 
@JsonIgnoreProperties(ignoreUnknown = true)  // Ignora campos extras en el JSON
public class Pedido {

    @JsonProperty("order_id")     // JSON: "order_id" <-> Java: orderId
    private String orderId;        // <-- sera la KEY de Kafka

    private String clienteId;
    private String producto;
    private double total;
    private String estado;          // CREADO | PAGADO | ENVIADO | ENTREGADO
    private long timestamp;

    // Constructor vacio requerido por Jackson para deserializar
    public Pedido() {}
}
@JsonProperty("order_id"): El campo se llama orderId en Java pero order_id en JSON. Sin esta anotacion, Jackson esperaria orderId en el JSON y fallaria al parsear.
@JsonIgnoreProperties(ignoreUnknown = true): Si el JSON contiene campos que no existen en la clase Java, Jackson los ignora en vez de lanzar excepcion. Util para evolucion de schema.
CampoTipoRol en Kafka
orderIdStringKEY del ProducerRecord. Determina la particion via murmur2 hash.
estadoStringCambia en cada evento: CREADO, PAGADO, ENVIADO, ENTREGADO. El consumer reconstruye el estado leyendo eventos en orden.
totaldoubleEn la leccion DLT, pedidos con total > $200 fallan la validacion y van al Dead Letter Topic.
timestamplongEpoch ms. Se actualiza cada vez que el estado cambia.

Configuracion del Producer

Propiedades usadas en PedidoEstadoProducer.java con explicacion de cada una.

PropiedadValorPor que
bootstrap.servers localhost:9092 Direccion del broker. El producer usa esta direccion inicial para descubrir todo el cluster.
acks all El broker no confirma el mensaje hasta que TODAS las replicas in-sync lo tienen. Maxima durabilidad. Ver simulador abajo.
enable.idempotence true Evita duplicados: si el producer reintenta un envio por timeout, el broker detecta que ya lo tiene y no lo escribe dos veces.
key.serializer StringSerializer Convierte la KEY (orderId) de String a bytes para enviarla a Kafka.
value.serializer StringSerializer Convierte el VALUE (JSON del Pedido) de String a bytes.
ProducerRecord 
// ProducerRecord(topic, KEY, value)
new ProducerRecord<>(
    "pedidos-estados",    // topic destino
    pedido.getOrderId(),     // KEY = "ORD-001" → murmur2 → particion
    json                     // VALUE = JSON serializado del pedido
);

// El callback confirma en que particion y offset quedo
producer.send(record, (meta, ex) -> {
    System.out.printf("P%d offset=%d", meta.partition(), meta.offset());
});

Configuracion del Consumer

Propiedades usadas en los distintos consumers del proyecto.

PropiedadPedidoEstadoConsumerRebalanceoDemoPor que
group.id grupo-ciclovida grupo-rebalanceo Cada grupo tiene sus propios offsets. Grupos distintos = lecturas independientes del mismo topic.
auto.offset.reset earliest latest earliest: lee desde offset 0 (historial completo). latest: solo mensajes nuevos. Ver simulador abajo.
enable.auto.commit false true false = control manual con commitSync() (mas seguro). true = Kafka hace commit automatico cada 5s.
heartbeat.interval.ms default (3000) 1000 Frecuencia con que el consumer avisa al broker que sigue vivo. Valor bajo = deteccion rapida de consumer muerto.
session.timeout.ms default (45000) 6000 Si el broker no recibe heartbeat en este tiempo, declara al consumer muerto y dispara rebalanceo.

Simulador: acks=0 vs 1 vs all

Haz clic en cada modo para ver como cambia el comportamiento del broker al confirmar un mensaje.

Simulador de acks
B0 Leader
B1 Follower
B2 Follower
acks=all (usado en TiendaMax):
El producer espera a que el Leader Y todos los Followers in-sync confirmen la escritura. Maxima durabilidad: si el Leader cae, los datos ya estan replicados. Mas latencia pero cero perdida de datos.

Comparador: auto.offset.reset

Cuando un consumer nuevo (sin offset guardado) se une a un topic, esta propiedad decide donde empieza a leer.

earliest

Lee desde el offset 0 (el primer mensaje del topic). Reconstruye todo el historial.

Offset: [0, 1, 2, 3, 4, 5, 6, 7]
       ▲ empieza aqui

latest

Lee solo mensajes nuevos publicados despues de que el consumer se conecto.

Offset: [0, 1, 2, 3, 4, 5, 6, 7]
                           ▲ empieza aqui
Importante: auto.offset.reset solo aplica cuando el consumer no tiene offset guardado (grupo nuevo o offset expirado). Si el grupo ya tiene offset, el consumer continua desde donde se quedo.

Patron Consumer-Produce (DLT)

PedidoDLTConsumer.java es consumer Y producer al mismo tiempo. Lee de un topic, procesa, y los mensajes fallidos los publica al DLT.

poll()
pedidos-estados
→
procesarPedido()
validar total
→
send() al DLT
si falla
→
flush() + commitSync()
Orden critico: flush() ANTES de commitSync()
Si haces commit antes de flush, el offset avanza pero el mensaje al DLT puede no haberse enviado todavia. Si el proceso muere entre el commit y el flush, el mensaje se pierde para siempre.

Headers del DLT

Los headers transportan metadata del error sin modificar el VALUE original del mensaje:

Headers DLT 
ProducerRecord<String, String> dltRecord =
    new ProducerRecord<>(DLT_TOPIC, original.key(), original.value());

// Headers = metadata del error (como HTTP headers)
dltRecord.headers()
    .add("error-message",       errorMsg.getBytes(UTF_8))
    .add("original-topic",      original.topic().getBytes(UTF_8))
    .add("original-partition",  String.valueOf(original.partition()).getBytes(UTF_8))
    .add("original-offset",     String.valueOf(original.offset()).getBytes(UTF_8))
    .add("failed-at-ms",        String.valueOf(System.currentTimeMillis()).getBytes(UTF_8));

producer.send(dltRecord);
producer.flush();   // ANTES de commitSync()

    }

Shutdown Hook

Todos los consumers del proyecto usan un shutdown hook para cerrar limpiamente con Ctrl+C:

Shutdown Hook 
Thread mainThread = Thread.currentThread();
Runtime.getRuntime().addShutdownHook(new Thread(() -> {
    System.out.println("Cerrando consumer...");
    mainThread.interrupt();  // Rompe el poll() → sale del while
}));

// El try-with-resources cierra el consumer automaticamente
try (KafkaConsumer<...> consumer = new KafkaConsumer<>(props)) {
    while (!Thread.currentThread().isInterrupted()) {
        consumer.poll(Duration.ofMillis(1000));
    }
}
// Al salir del try: consumer.close() dispara un rebalanceo limpio
Por que importa el cierre limpio: Si el consumer muere sin cerrar, el broker tiene que esperar session.timeout.ms (6s en RebalanceoDemo) para declararlo muerto. Con consumer.close(), el rebalanceo ocurre inmediatamente.
PropiedadValor en RebalanceoDemoEfecto
heartbeat.interval.ms1000Envia heartbeat cada 1s. Deteccion rapida pero mas trafico de red.
session.timeout.ms6000Si no hay heartbeat en 6s, el consumer se considera muerto. Valores bajos = rebalanceo rapido pero sensible a pausas de GC.

Quiz de Configuracion

1. Si cambias acks de "all" a "0" en el producer, que consecuencia tiene?
Los mensajes se envian mas lento porque el broker procesa mas
El producer no espera confirmacion del broker. Mayor velocidad pero riesgo de perder mensajes si el broker cae
Los mensajes se replican a mas brokers automaticamente
El consumer deja de funcionar porque necesita acks=all
Correcto. Con acks=0 el producer hace "fire and forget". No sabe si el broker recibio el mensaje. Maximo throughput pero minima durabilidad.
Incorrecto. acks=0 significa que el producer no espera respuesta del broker. El mensaje puede perderse si el broker tiene problemas, pero la velocidad de envio aumenta significativamente.
2. Por que PedidoEstadoConsumer usa auto.offset.reset=earliest pero RebalanceoDemo usa latest?
Es un error de configuracion, ambos deberian usar el mismo
latest es mas rapido que earliest
El consumer de ciclo de vida necesita todo el historial para reconstruir estado. El de rebalanceo solo necesita ver mensajes nuevos para demostrar la redistribucion
earliest solo funciona con enable.auto.commit=false
Correcto. Event Sourcing requiere leer desde el inicio para reconstruir el estado. El demo de rebalanceo solo necesita observar actividad en tiempo real.
Incorrecto. Cada consumer tiene un proposito distinto: reconstruir estado (earliest) vs observar rebalanceo en vivo (latest). La eleccion depende del caso de uso.
3. En PedidoDLTConsumer, por que es critico hacer flush() antes de commitSync()?
flush() es necesario para que el consumer funcione correctamente
Sin flush(), el consumer no puede hacer poll() de nuevo
Si haces commit antes de flush y el proceso muere, el offset avanza pero el mensaje al DLT puede no haberse enviado: se pierde para siempre
flush() y commitSync() son intercambiables, el orden no importa
Correcto. flush() garantiza que el mensaje llego al DLT. Solo despues es seguro avanzar el offset con commitSync(). El orden protege contra perdida de mensajes.
Incorrecto. El orden flush() → commitSync() es critico: primero aseguras que el DLT tiene el mensaje fallido, luego avanzas el offset. Invertirlo puede causar perdida de datos.
4. Que significa KAFKA_PROCESS_ROLES: broker,controller en docker-compose.yml?
El nodo cumple ambos roles simultaneamente (modo combinado KRaft). En produccion se separan en nodos distintos
Kafka arranca dos procesos separados dentro del mismo contenedor
Es equivalente a usar ZooKeeper como controller externo
Solo el rol de broker esta activo, controller es un fallback
Correcto. Modo combinado: un solo nodo actua como broker (recibe mensajes) y controller (gestiona metadata). Ideal para desarrollo. En produccion se usan nodos dedicados para cada rol.
Incorrecto. En KRaft, broker,controller significa modo combinado: el mismo proceso JVM maneja ambos roles. No hay ZooKeeper involucrado.
