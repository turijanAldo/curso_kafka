Ciclo de Vida de un Pedido con Kafka

Aprende como Event Sourcing y las KEYs de Kafka garantizan el orden de los eventos de un pedido en TiendaMax.

Reconstruir el estado de un pedido desde la secuencia de eventos

KEY y Particiones

Cada mensaje en Kafka tiene una KEY opcional. Cuando produces un mensaje con KEY, Kafka aplica un hash (murmur2) para determinar a cual particion va. La misma KEY siempre va a la misma particion.

partition = murmur2(KEY) % numPartitions
💡
Implicacion clave: Si usas el orderId como KEY, todos los eventos de un mismo pedido terminan en la misma particion, garantizando su orden cronologico.

Orden Garantizado por Particion

Kafka garantiza el orden de los mensajes dentro de una particion. Los mensajes se entregan en el mismo orden en que fueron escritos. Si todos los eventos de un pedido van a la misma particion (gracias a la KEY), el consumidor los ve en orden cronologico.

Event Sourcing Basico

En lugar de almacenar solo el estado actual en una base de datos, Event Sourcing almacena todos los eventos que modifican el estado. El consumidor reconstruye el estado actual leyendo los eventos en orden.

Quiz de Reflexion

Pon a prueba tu comprension de los conceptos de esta leccion.

1. ¿Que pasa si envias los eventos de ORD-001 sin KEY?
Todos van a la particion 0 por defecto
Se distribuyen round-robin entre particiones, rompiendo el orden
Kafka los rechaza con un error
Van todos a una particion aleatoria fija
✅ Correcto. Sin KEY, Kafka usa round-robin y los eventos del mismo pedido pueden caer en particiones diferentes, perdiendo la garantia de orden.
❌ Incorrecto. Sin KEY, Kafka distribuye round-robin entre particiones. Los eventos se dispersan y el orden se rompe.
2. ¿Puede el consumer ver ENTREGADO antes que CREADO para el mismo pedido?
Si, Kafka no garantiza orden nunca
No, si ambos usan la misma KEY van a la misma particion y se leen en orden
Solo si hay mas de 3 particiones
✅ Correcto. Con la misma KEY, todos los eventos van a la misma particion y Kafka garantiza el orden FIFO dentro de ella.
❌ Incorrecto. Cuando usas la misma KEY, los eventos van a la misma particion y se leen en el orden exacto en que fueron escritos.
3. Si agregas una 4a particion al topic, ¿ORD-001 sigue en la particion 0?
Si, la particion asignada nunca cambia
No necesariamente, porque hash % N cambia al cambiar N
Si, porque murmur2 es deterministico
✅ Correcto. Aunque murmur2 produce el mismo hash, el resultado de hash % 4 puede ser diferente de hash % 3. Por eso cambiar el numero de particiones puede reasignar las KEYs.
❌ Incorrecto. La formula es hash % numPartitions. Si cambias numPartitions, el resultado del modulo puede cambiar aunque el hash sea el mismo.
4. ¿Cual es la principal ventaja de reconstruir el estado desde eventos?
Es mas rapido que una base de datos relacional
Usa menos espacio en disco
Tienes el historial completo y puedes rebobinar a cualquier punto en el tiempo
No necesitas un consumer group
✅ Correcto. Event Sourcing conserva todo el historial de cambios, permitiendo auditar, rebobinar y reproducir la secuencia completa de eventos.
❌ Incorrecto. La ventaja principal de Event Sourcing es el historial completo: puedes reconstruir el estado a cualquier punto y auditar cada cambio.

Practica en Terminal

Ahora que entiendes los conceptos con los simuladores, ejecuta la practica real con Kafka y Java. Necesitas 2 terminales abiertas en la carpeta kafka-week/tiendamax/.

Prerrequisitos
RequisitoVerificacion
Kafka corriendo en Dockerdocker ps muestra el contenedor kafka
Puerto 9092 accesibleEl contenedor expone 0.0.0.0:9092
Java 17+ instaladojava -version
Maven instaladomvn -version
📄
Archivos de codigo: PedidoEstadoProducer.java (producer del ciclo de vida) y PedidoEstadoConsumer.java (consumer que reconstruye estado). Ambos en tiendamax/src/main/java/com/tiendamax/.

Paso 1 — Crear el topic

El topic pedidos-estados tiene 3 particiones (una por cada pedido del ejemplo).

Terminal docker exec -it kafka bash /opt/kafka/bin/kafka-topics.sh \ --create \ --topic pedidos-estados \ --partitions 3 \ --replication-factor 1 \ --bootstrap-server localhost:9092 # Verificar que se creo: /opt/kafka/bin/kafka-topics.sh \ --describe \ --topic pedidos-estados \ --bootstrap-server localhost:9092 exit
✅
Deberias ver: Topic: pedidos-estados PartitionCount: 3 ReplicationFactor: 1 con 3 particiones listadas.

Paso 2 — Compilar

Terminal mvn compile -q

Paso 3 — Lanzar el Consumer (Terminal A)

Lanza el consumer antes que el producer para observar los mensajes llegar en tiempo real.

Terminal A mvn exec:java "-Dexec.mainClass=com.tiendamax.PedidoEstadoConsumer"

Salida esperada:

Salida Escuchando [pedidos-estados] como grupo [grupo-ciclovida] Reconstruyendo estado desde eventos...

Paso 4 — Lanzar el Producer (Terminal B)

Terminal B mvn exec:java "-Dexec.mainClass=com.tiendamax.PedidoEstadoProducer"

Salida esperada del producer:

Salida Producer Emitiendo ciclo de vida para 3 pedidos... KEY = orderId -> todos los eventos de un pedido van a la MISMA particion -- Transicion: CREADO -- OK ORD-001 CREADO -> P0 offset=0 OK ORD-002 CREADO -> P1 offset=0 OK ORD-003 CREADO -> P2 offset=0 -- Transicion: PAGADO -- OK ORD-001 PAGADO -> P0 offset=1 OK ORD-002 PAGADO -> P1 offset=1 OK ORD-003 PAGADO -> P2 offset=1
🔎
Que observar: ORD-001 siempre aparece en P0, ORD-002 en P1. El offset aumenta dentro de cada particion — eso es el orden cronologico en Kafka. Compara esto con lo que viste en el simulador de arriba.

Salida esperada del consumer (Terminal A):

Salida Consumer -- Poll: 3 eventos recibidos -- P0 offset=0 ORD-001 NINGUNO -> CREADO P1 offset=0 ORD-002 NINGUNO -> CREADO P2 offset=0 ORD-003 NINGUNO -> CREADO Estado actual reconstruido desde eventos: ORD-001 CREADO (fijo en P0) ORD-002 CREADO (fijo en P1) ORD-003 CREADO (fijo en P2)
💡
La seccion "Estado actual reconstruido" es la proyeccion: el resumen del estado mas reciente de cada pedido, construido solo a partir de los eventos del topic. Es lo mismo que la tabla "Estado reconstruido" del simulador.
