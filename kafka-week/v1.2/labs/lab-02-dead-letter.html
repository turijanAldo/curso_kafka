Dead Letter Topic (DLT)

Cuando un consumidor no puede procesar un mensaje, necesita una estrategia inteligente. El Dead Letter Topic es el patron que evita perder datos y bloquear el pipeline.

1
Entender por que ignorar o reintentar infinitamente son malas estrategias
2
Implementar el patron DLT con headers de error
3
Dominar el orden: send DLT, flush, commitSync
4
Inspeccionar headers de Kafka en mensajes DLT

El Problema

Un consumidor recibe un mensaje que no puede procesar (datos invalidos, servicio externo caido, regla de negocio violada). Que hace?

❌ Estrategia 1: Ignorar el error + commit

Se atrapa la excepcion, se hace commit y se sigue adelante. El mensaje se pierde para siempre. Nadie sabe que fallo. No hay forma de reprocesar.

⚠️ Estrategia 2: Reintentar infinitamente

Se reintenta el mismo mensaje una y otra vez. El consumidor se bloquea. El consumer lag crece. Los mensajes detras se acumulan sin procesarse.

✅ Estrategia 3: Enviar al DLT + commit + continuar

Se envia el mensaje fallido a un topic especial (DLT) con metadata del error, se hace commit y se continua con el siguiente mensaje. Nada se pierde, nada se bloquea.

Dead Letter Topic

Que es un Dead Letter Topic

Es un topic separado de Kafka donde se envian los mensajes que el consumidor no pudo procesar. Cada mensaje lleva headers con metadata del error para facilitar el diagnostico.

📖
Convencion de nombres: Si el topic original es pedidos-estados, el DLT se llama pedidos-estados-dlt. Sufijo -dlt.
Producer
→
pedidos-estados
→
Consumer DLT
→
pedidos-estados-dlt
💡
El consumidor nunca se bloquea. El mensaje va al DLT, se hace commit y el consumidor sigue con el siguiente registro. Un equipo de operaciones puede revisar el DLT despues y decidir si reprocesar.

Headers de Kafka

Un mensaje de Kafka tiene 3 partes: KEY, VALUE y HEADERS. Los headers son pares clave-valor en bytes, similares a los headers HTTP. Son ideales para metadata sin modificar el payload original.

Key
"ORD-001"
Value (JSON)
{"order_id":"ORD-001",
"producto":"Laptop",
"total":1299,
"estado":"CREADO"}
Headers
error-message: "Total $1299 excede limite"
original-topic: "pedidos-estados"
original-partition: "0"
original-offset: "0"
failed-at-ms: "1716230400000"
⚠️
Por que headers y no modificar el JSON? Porque si modificas el VALUE, pierdes el mensaje original. Con headers, el VALUE queda intacto para poder hacer replay.

Orden de Operaciones

El orden importa. Si haces commitSync antes de confirmar que el DLT recibio el mensaje, puedes perder datos.

1. producer.send(dlt)
→
2. producer.flush()
→
3. consumer.commitSync()
⚠️
flush() antes de commitSync() — flush() garantiza que el mensaje llego al DLT antes de marcar el offset como consumido. Si inviertes el orden y el envio al DLT falla, el mensaje se pierde.
Java try { procesarPedido(pedido); // puede lanzar excepcion } catch (Exception e) { ProducerRecord<String, String> dltRecord = new ProducerRecord<>("pedidos-estados-dlt", key, value); dltRecord.headers() .add("error-message", e.getMessage().getBytes()) .add("original-topic", "pedidos-estados".getBytes()) .add("original-partition", String.valueOf(partition).getBytes()) .add("original-offset", String.valueOf(offset).getBytes()); producer.send(dltRecord); // 1. Enviar al DLT producer.flush(); // 2. Esperar confirmacion consumer.commitSync(); // 3. Marcar como consumido }

Practica en Terminal

Ejecuta la practica real con Kafka. Necesitas 3 terminales abiertas en kafka-week/tiendamax/.

Prerrequisitos
RequisitoVerificacion
Leccion 1 completadaEl topic pedidos-estados existe y tiene mensajes
Kafka corriendo en Dockerdocker ps muestra el contenedor kafka
Proyecto compiladomvn compile -q sin errores
📄
Archivo de codigo: PedidoDLTConsumer.java en tiendamax/src/main/java/com/tiendamax/. Este consumer lee de pedidos-estados y envia los fallidos a pedidos-estados-dlt. Reutilizamos el producer PedidoEstadoProducer.java de la leccion anterior.

Paso 1 — Crear el topic DLT

El topic DLT es un topic normal. La convencion es agregar el sufijo -dlt al topic original.

Terminal docker exec kafka /opt/kafka/bin/kafka-topics.sh \ --create \ --topic pedidos-estados-dlt \ --partitions 3 \ --replication-factor 1 \ --bootstrap-server localhost:9092 # Verificar que ambos topics existen: docker exec kafka /opt/kafka/bin/kafka-topics.sh \ --list \ --bootstrap-server localhost:9092
✅
Deberias ver ambos topics: pedidos-estados y pedidos-estados-dlt.

Paso 2 — Compilar

Terminal mvn compile -q

Paso 3 — Lanzar el Consumer DLT (Terminal A)

Terminal A mvn exec:java "-Dexec.mainClass=com.tiendamax.PedidoDLTConsumer"

Salida esperada:

Salida Consumer DLT escuchando [pedidos-estados] Mensajes que fallen iran a [pedidos-estados-dlt] Regla: pedidos con total > $200.0 requieren aprobacion manual

Paso 4 — Lanzar el Producer (Terminal B)

Reutilizamos el producer de la leccion anterior. Si el topic ya tiene mensajes, el consumer DLT los leera desde el principio porque usa un group.id distinto (grupo-dlt).

Terminal B mvn exec:java "-Dexec.mainClass=com.tiendamax.PedidoEstadoProducer"

Salida esperada del Consumer DLT (Terminal A):

Salida Consumer DLT -- Poll: 3 mensajes -- DLT P0 offset=0 ORD-001 -> [pedidos-estados-dlt] Requiere aprobacion manual: total $1299.0 supera el limite $200.0 OK P1 offset=0 ORD-002 $89.00 CREADO DLT P2 offset=0 ORD-003 -> [pedidos-estados-dlt] Requiere aprobacion manual: total $399.0 supera el limite $200.0 Commit realizado. Continuando con los siguientes mensajes.
🔎
Que observar: DLT indica redireccion al Dead Letter Topic. OK indica procesamiento exitoso. El consumer nunca se bloquea: procesa lo que puede, redirige lo que no, hace commit y continua. Compara esto con el simulador de arriba.

Paso 5 — Inspeccionar el DLT (Terminal C)

Abre una tercera terminal para ver los mensajes que llegaron al DLT:

Terminal C # Ver mensajes del DLT (solo valor): docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh \ --topic pedidos-estados-dlt \ --from-beginning \ --bootstrap-server localhost:9092 # Ver mensajes del DLT CON headers: docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh \ --topic pedidos-estados-dlt \ --from-beginning \ --property print.headers=true \ --bootstrap-server localhost:9092
💡
El VALUE es el JSON original sin modificar. Los headers (error-message, original-topic, etc.) solo se ven con la opcion --property print.headers=true. Esto es lo mismo que el Inspector de Headers del simulador.

Quiz de Reflexion

Pon a prueba lo que aprendiste sobre Dead Letter Topics.

1. Por que se llama flush() antes de commitSync()?
Para mejorar el rendimiento del producer
Para garantizar que el mensaje llego al DLT antes de marcar el offset como consumido
Porque Kafka lo requiere por configuracion
Para liberar memoria del buffer del producer
Correcto. flush() bloquea hasta que el broker confirma la escritura al DLT. Solo entonces es seguro hacer commitSync().
Incorrecto. La razon es garantizar que el mensaje llego al DLT antes de marcar el offset. Si haces commit primero y el envio falla, pierdes el mensaje.
2. Por que se usan headers en lugar de modificar el JSON del mensaje?
Porque los headers son mas rapidos de serializar
Porque Kafka no permite modificar el value
Para mantener el value original intacto y poder hacer replay
Porque los headers se comprimen automaticamente
Correcto. El value original se preserva sin cambios. Los headers agregan metadata del error sin contaminar el payload, permitiendo reprocesar el mensaje tal cual.
Incorrecto. La razon principal es preservar el value original intacto para poder hacer replay del mensaje sin alteraciones.
3. Que pasa si el envio al DLT tambien falla?
El consumidor reintenta automaticamente
Kafka redirige al DLT internamente
En el codigo actual, el mensaje se pierde (no se maneja ese caso)
El mensaje vuelve al topic original
Correcto. En la implementacion basica, si el send al DLT falla, la excepcion se propaga y el mensaje podria perderse. En produccion se agregan reintentos y alertas.
Incorrecto. En el codigo actual no hay manejo adicional: si el DLT falla, el mensaje se pierde. Esto es una limitacion conocida de la implementacion basica.
4. Cuantas veces puede aparecer el mismo pedido en el DLT?
Maximo una vez
Depende del numero de particiones
Tantas veces como eventos de ese pedido fallen
Exactamente 3 veces (por los reintentos)
Correcto. Cada evento (CREADO, PAGADO, ENVIADO, ENTREGADO) que falle genera una entrada independiente en el DLT. Un pedido con 4 estados fallidos apareceria 4 veces.
Incorrecto. El DLT recibe cada evento que falla individualmente. Si un pedido tiene multiples eventos que fallan, cada uno genera su propia entrada en el DLT.
