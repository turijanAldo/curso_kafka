Consumer Group

Un conjunto de consumers que cooperan para leer un topic. Kafka divide el trabajo automaticamente: cada mensaje es procesado por exactamente un consumer del grupo.

🔍 Analogia

Imagina una pizzeria con 3 hornos (particiones) y un equipo de repartidores (consumers). Cada horno entrega pizzas a un solo repartidor. Si llega un repartidor nuevo, se redistribuyen los hornos. Si un repartidor se va, otro cubre sus hornos.

La Regla Fundamental

Una particion solo puede ser leida por un consumer activo dentro de un mismo grupo. Esto establece el limite del paralelismo.

⚠️
Maximo de consumers utiles = numero de particiones.
Si tienes 3 particiones, el consumer #4 quedara inactivo (standby). No recibira mensajes hasta que otro consumer falle.
Regla 1 particion → 1 consumer activo por grupo consumers > particiones → consumers sobrantes = INACTIVOS consumers < particiones → algun consumer lee mas de 1 particion

Rebalanceo

Cuando la membresia del grupo cambia, Kafka redistribuye las particiones entre los consumers activos. Este proceso se llama rebalanceo.

⚡ Triggers del rebalanceo
  • Un consumer se une al grupo
  • Un consumer sale del grupo (crash o shutdown)
  • Se agregan nuevas particiones al topic
🛑
Stop-the-world: Durante el rebalanceo, ningun consumer del grupo lee mensajes. Por eso es importante minimizar la frecuencia de rebalanceos en produccion.

ConsumerRebalanceListener

Java proporciona un listener con dos callbacks para reaccionar al rebalanceo.

Java consumer.subscribe(List.of("pedidos"), new ConsumerRebalanceListener() { @Override public void onPartitionsRevoked(Collection<TopicPartition> partitions) { // ANTES del rebalanceo: hacer commit final consumer.commitSync(); log.info("Particiones REVOCADAS: {}", partitions); } @Override public void onPartitionsAssigned(Collection<TopicPartition> partitions) { // DESPUES del rebalanceo: inicializar estado log.info("Particiones ASIGNADAS: {}", partitions); } });
💡
onPartitionsRevoked es tu ultima oportunidad para hacer commit de offsets antes de perder las particiones. Si no lo haces, podrias reprocesar mensajes.

Practica en Terminal

Ahora ejecuta el experimento real con multiples instancias del consumer. Necesitas 3 o 4 terminales abiertas en kafka-week/tiendamax/.

Prerrequisitos
RequisitoVerificacion
Topic pedidos-estados existeCreado en Leccion 1 con 3 particiones
Kafka corriendo en Dockerdocker ps muestra el contenedor kafka
Proyecto compiladomvn compile -q sin errores
📄
Archivo de codigo: RebalanceoDemo.java en tiendamax/src/main/java/com/tiendamax/. Implementa un ConsumerRebalanceListener que imprime las particiones revocadas y asignadas en cada rebalanceo.

Paso 1 — Verificar el topic

Terminal docker exec kafka /opt/kafka/bin/kafka-topics.sh \ --describe --topic pedidos-estados \ --bootstrap-server localhost:9092
✅
Debe mostrar 3 particiones. Si no existe, crealo con el comando de la Leccion 1.

Paso 2 — Compilar

Terminal mvn compile -q

Paso 3 — Lanzar instancia 1 (Terminal 1)

Terminal 1 mvn exec:java "-Dexec.mainClass=com.tiendamax.RebalanceoDemo"

Salida esperada:

Salida Consumer iniciado. Grupo: [grupo-rebalanceo] Esperando asignacion de particiones... >>> REBALANCEO COMPLETADO <<< Particiones ASIGNADAS a este consumer: - pedidos-estados [P0] - pedidos-estados [P1] - pedidos-estados [P2]
🔎
El primer consumer recibe las 3 particiones porque es el unico en el grupo. Esto es lo mismo que agregar Consumer-1 en el simulador de arriba.

Paso 4 — Lanzar instancia 2 (Terminal 2)

Terminal 2 mvn exec:java "-Dexec.mainClass=com.tiendamax.RebalanceoDemo"

Observa ambas terminales. Las dos imprimen el rebalanceo:

Terminal 1 (consumer existente) >>> REBALANCEO INICIADO <<< Particiones REVOCADAS (me las quitaron): - pedidos-estados [P0] - pedidos-estados [P1] - pedidos-estados [P2] >>> REBALANCEO COMPLETADO <<< Particiones ASIGNADAS a este consumer: - pedidos-estados [P0] - pedidos-estados [P1]
Terminal 2 (consumer nuevo) >>> REBALANCEO COMPLETADO <<< Particiones ASIGNADAS a este consumer: - pedidos-estados [P2]

Paso 5 — Lanzar instancia 3 (Terminal 3)

Ahora hay 3 consumers y 3 particiones: cada uno recibe exactamente 1 particion (paralelismo maximo).

Terminal 3 mvn exec:java "-Dexec.mainClass=com.tiendamax.RebalanceoDemo"

Paso 6 (opcional) — Lanzar instancia 4

El 4o consumer queda inactivo — no hay particiones disponibles para el.

Salida del 4o consumer >>> REBALANCEO COMPLETADO <<< Sin particiones asignadas. Hay mas consumers que particiones en el grupo. Este consumer esta INACTIVO hasta que salga otro del grupo.

Paso 7 — Matar un consumer (Ctrl+C en Terminal 1)

Las terminales restantes imprimen el rebalanceo automaticamente. Las particiones del consumer muerto se redistribuyen.

Salida en terminales restantes [SHUTDOWN] Cerrando consumer - esto disparara un rebalanceo en el grupo. >>> REBALANCEO INICIADO <<< Particiones REVOCADAS (me las quitaron): ... >>> REBALANCEO COMPLETADO <<< Particiones ASIGNADAS a este consumer: - pedidos-estados [P0] <- absorbe la particion del consumer que salio
💡
Si tenias el 4o consumer inactivo, ahora recibira una particion. Esto es exactamente lo que ves en el simulador cuando matas un consumer.

Paso 8 — Ver estado del grupo desde CLI

Mientras las instancias estan corriendo, abre otra terminal:

Terminal extra # Ver todos los consumer groups docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \ --list --bootstrap-server localhost:9092 # Ver detalle: que consumer tiene cada particion y su LAG docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \ --describe --group grupo-rebalanceo \ --bootstrap-server localhost:9092
📈
La columna LAG muestra cuantos mensajes tiene pendientes cada consumer. Un lag alto indica que el consumer no esta al dia. Esto es lo que simula el Visualizador de Lag de arriba.

Quiz de Reflexion

Pon a prueba lo que aprendiste.

1. Si un topic tiene 3 particiones y 5 consumers en el mismo grupo, ¿cuantos consumers quedan inactivos?
0 — todos reciben mensajes
1 — solo uno queda sin particion
2 — solo 3 pueden estar activos
5 — ninguno puede leer
✅ Correcto. Maximo de consumers activos = numero de particiones. 5 - 3 = 2 inactivos.
❌ Incorrecto. Con 3 particiones, maximo 3 consumers estan activos. Los 2 restantes quedan en standby.
2. ¿Que ocurre durante un rebalanceo?
Solo el consumer nuevo deja de leer
Ningun consumer del grupo lee mensajes (stop-the-world)
Los consumers existentes siguen leyendo normalmente
El broker deja de recibir mensajes del producer
✅ Correcto. El rebalanceo es un stop-the-world: todos los consumers del grupo pausan su lectura mientras se redistribuyen las particiones.
❌ Incorrecto. Durante el rebalanceo TODOS los consumers del grupo dejan de leer (stop-the-world). Es una pausa total.
3. ¿Para que sirve el callback onPartitionsRevoked?
Para inicializar el estado del nuevo consumer
Para agregar nuevas particiones al topic
Para hacer commit final de offsets antes de soltar las particiones
Para notificar al producer que deje de enviar
✅ Correcto. onPartitionsRevoked es tu ultima oportunidad para hacer commit antes de que las particiones pasen a otro consumer.
❌ Incorrecto. onPartitionsRevoked se invoca ANTES del rebalanceo para que hagas commit final y no pierdas progreso.
4. Comparado con IBM MQ, ¿cual es la diferencia clave en el modelo de consumers?
IBM MQ no soporta multiples consumers
Kafka no permite mas de un consumer por topic
En Kafka el paralelismo esta limitado por particiones; en MQ cualquier numero de consumers compite por los mensajes
No hay diferencia, ambos usan particiones
✅ Correcto. En MQ los consumers compiten libremente por mensajes de la cola. En Kafka, el paralelismo maximo esta definido por la cantidad de particiones.
❌ Incorrecto. La diferencia clave es que Kafka limita el paralelismo al numero de particiones, mientras que en IBM MQ multiples consumers compiten sin ese limite.
