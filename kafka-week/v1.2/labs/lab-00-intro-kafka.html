Que es Apache Kafka

Apache Kafka es una plataforma distribuida de streaming de eventos. Permite publicar, almacenar y procesar flujos de datos en tiempo real.

⚙
Analogia: la cinta transportadora de una fabrica.
Los productos (mensajes) se colocan en la cinta (topic). Multiples estaciones (consumers) pueden leer los productos sin quitarlos de la cinta. Cada estacion lee a su propio ritmo.
Kafka vs Colas Tradicionales (RabbitMQ, IBM MQ)

En una cola tradicional, cuando un consumer lee un mensaje, este se borra. En Kafka, los mensajes permanecen en disco despues de ser consumidos.

❌
Cola tradicional: consume → mensaje eliminado. Un solo consumer por mensaje.
✅
Kafka: consume → mensaje permanece. Replay, multiples consumers, auditoria.
Casos de uso
Pagos — Procesar transacciones en tiempo real
E-commerce — Seguimiento de pedidos y eventos
Monitoreo — Metricas y logs centralizados
Redes sociales — Feeds y notificaciones

KRaft vs ZooKeeper

Antes, Kafka necesitaba ZooKeeper para coordinar metadata del cluster. Desde Kafka 4.x, KRaft elimina esa dependencia — Kafka se coordina solo.

Antes (ZooKeeper)
❌ Dos sistemas separados
❌ Configuracion compleja
❌ Limite de ~200K particiones
❌ Recuperacion lenta
❌ Requiere monitorear 2 clusters
→
Ahora (KRaft)
✅ Un solo sistema
✅ Operacion simple
✅ Millones de particiones
✅ Recuperacion rapida (Raft)
✅ Inicio mas rapido
💡
KRaft usa el protocolo Raft para elegir un controller lider entre los nodos. En nuestro entorno local, un solo nodo actua como broker y controller al mismo tiempo.

Topics y Particiones

Un topic es un canal logico de mensajes. Cada topic se divide en particiones, que son la unidad de paralelismo en Kafka.

Caracteristicas clave
  • Los mensajes dentro de una particion estan ordenados e inmutables.
  • Cada mensaje tiene un offset (numero de posicion unico).
  • Sin KEY = los mensajes se distribuyen en round-robin entre particiones.
  • Con KEY = todos los mensajes con la misma key van a la misma particion.
  • Mas particiones = mas paralelismo (mas consumers pueden leer a la vez).

Offsets

El offset es el numero de posicion de cada mensaje dentro de una particion. Los consumer groups guardan su offset actual en un topic interno: __consumer_offsets.

auto.offset.reset

Cuando un consumer nuevo se conecta sin offset previo guardado:

⏮
earliest — Lee desde el inicio (offset 0). Equivalente a --from-beginning.
⏩
latest — Solo lee mensajes nuevos (por defecto).

Replication Factor

El replication factor define cuantas copias de cada particion existen en el cluster.

Comparacion
Factor Copias Tolerancia a fallos Uso
1 Solo 1 copia Ninguna — si el broker cae, se pierden datos Desarrollo local
2 2 copias 1 broker puede fallar Pre-produccion
3 3 copias 2 brokers pueden fallar Produccion (recomendado)
⚠
En nuestro entorno local con un solo broker, usamos replication-factor 1. En produccion, siempre usa al menos 3.

Flujo Producer → Broker → Consumer

El recorrido completo de un mensaje paso a paso.

  1. Connect — El Producer se conecta al broker (bootstrap-server).
  2. Send — El Producer envia un record (key + value) al topic.
  3. Partition assignment — El broker determina la particion (hash de key o round-robin).
  4. Write to disk — El mensaje se escribe al log de la particion en disco.
  5. ACK — El broker confirma la escritura al Producer.
  6. Poll — El Consumer hace poll() al broker pidiendo mensajes.
  7. Deliver — El broker entrega los mensajes desde el offset actual del consumer.
  8. Commit offset — El consumer guarda su posicion en __consumer_offsets.
1. Producer
connect + send
→
2. Broker
partition + write + ACK
→
3. Consumer
poll + deliver + commit

Persistencia

Los mensajes de Kafka se almacenan en disco, no en memoria. En Docker, se persisten en un volumen.

Detalles
  • Retencion por defecto: 7 dias (log.retention.hours=168).
  • docker compose down → contenedor se detiene, datos sobreviven en el volumen.
  • docker compose down -v → contenedor se detiene y se borran los datos.
⚠
Cuidado con -v: borra los volumenes Docker y con ellos todos los mensajes de todos los topics. Usalo solo cuando quieras empezar desde cero.

Practica en Terminal

Sigue estos pasos para levantar un cluster Kafka real con Docker y enviar tus primeros mensajes.

⚠
Prerequisitos: Docker Desktop 24+ y Docker Compose v2+ instalados y corriendo.
1
Levantar el cluster
cd kafka-week/infra && docker compose up -d
Espera ~20-30 segundos para que Kafka inicie completamente.
2
Verificar que Kafka inicio
docker compose logs kafka
Busca el mensaje "started" o "Kafka Server started" en los logs.
3
Entrar al contenedor
docker exec -it kafka bash
export PATH=$PATH:/opt/kafka/bin/
kafka-topics.sh --bootstrap-server localhost:9092 --list
Veras un prompt de bash dentro del contenedor.
4
Crear un topic
kafka-topics.sh --create --topic test-topic \ --partitions 3 --replication-factor 1 \ --bootstrap-server localhost:9092
Created topic test-topic.
5
Listar topics
kafka-topics.sh --list --bootstrap-server localhost:9092
test-topic
6
Terminal 1 — Iniciar Producer
kafka-console-producer.sh --topic test-topic \ --bootstrap-server localhost:9092
Aparece un prompt > donde puedes escribir mensajes.
7
Terminal 2 — Iniciar Consumer
kafka-console-consumer.sh --topic test-topic \ --from-beginning \ --bootstrap-server localhost:9092
docker exec -it kafka /opt/kafka/bin/kafka-console-consumer.sh \ --topic test-topic --from-beginning \ --bootstrap-server localhost:9092
Los mensajes que escribas en Terminal 1 apareceran aqui.
8
Enviar mensajes
En Terminal 1, escribe mensajes y presiona Enter. Observa como aparecen en Terminal 2.
9
Describir el topic
kafka-topics.sh --describe --topic test-topic \ --bootstrap-server localhost:9092
Muestra particiones, lider y replicas del topic.
10
Consumer con grupo
kafka-console-consumer.sh --topic test-topic \ --group mi-grupo \ --bootstrap-server localhost:9092
Consumer asociado al grupo "mi-grupo". El offset se guarda automaticamente.
11
Detener el cluster
# Mantener datos: docker compose down # Borrar todo (volumenes incluidos): docker compose down -v

Troubleshooting

Problemas comunes y sus soluciones.

❌ "Connection refused" al conectar al broker
Kafka tarda 20-30 segundos en iniciar. Espera y verifica con docker compose logs kafka que diga "started".
❌ Consumer no recibe mensajes
Verifica que usas el mismo nombre de topic y el mismo --bootstrap-server localhost:9092. Si el consumer inicio despues de los mensajes, agrega --from-beginning.
❌ "Topic already exists"
Esto es normal si el topic ya fue creado. Puedes ignorar el error o agregar --if-not-exists al comando de creacion.
❌ Container no arranca
Verifica que el puerto 9092 no este ocupado por otro proceso: lsof -i :9092 (Mac/Linux) o netstat -ano | findstr 9092 (Windows).

Quiz de Reflexion

Verifica lo que aprendiste.

1. Cual es la diferencia principal entre Kafka y una cola de mensajes tradicional?
Kafka es mas rapido que las colas tradicionales
Kafka no borra los mensajes despues de consumirlos
Kafka solo funciona con Java
Correcto. Kafka retiene los mensajes en disco, permitiendo replay, multiples consumers y auditoria.
Incorrecto. La diferencia clave es que Kafka retiene los mensajes despues de ser consumidos.
2. Por que KRaft reemplaza a ZooKeeper?
ZooKeeper es un software de pago
KRaft permite usar mas lenguajes de programacion
Operacion mas simple: un solo sistema en vez de dos
Correcto. KRaft integra la coordinacion directamente en Kafka, eliminando la complejidad de mantener ZooKeeper por separado.
Incorrecto. La razon principal es simplificar la operacion eliminando un sistema externo.
3. Si envias mensajes sin KEY a un topic con 3 particiones, como se distribuyen?
Todos van a la particion 0
Se distribuyen en round-robin entre las 3 particiones
Kafka elige la particion con menos mensajes
Correcto. Sin key, Kafka usa round-robin (o sticky partitioner) para distribuir mensajes equitativamente.
Incorrecto. Sin key, la distribucion es round-robin entre todas las particiones.
4. Que pasa si ejecutas docker compose down -v?
Solo detiene el contenedor, los datos sobreviven
Reinicia Kafka con la configuracion por defecto
Se borran todos los mensajes persistidos (volumenes eliminados)
Correcto. La flag -v elimina los volumenes Docker y con ellos todos los datos de Kafka.
Incorrecto. La flag -v elimina los volumenes, borrando todos los datos persistidos.
