Particionado y replicado. Muchos productores escriben.
Muchos consumidores leen a su propio ritmo.

BLOQUE 2 · FUNDAMENTOS

Producer, Consumer, Consumer Group

topic (3 particiones) ┌───┬───┬───┐ producer ────→ │ P0 │ P1 │ P2 │ └─┬─┴─┬─┴─┬─┘ │ │ │ ▼ ▼ ▼ consumer-A consumer-B consumer-C └──────── group "inventario" ────────┘
  • Consumers del mismo group se reparten particiones.
  • Más consumers que particiones → los extras quedan en standby.
  • Otro group = lee todo desde su propio offset (servicios independientes).

Anatomía de un Producer

Properties props = new Properties();
props.put("bootstrap.servers",  "localhost:9092");
props.put("key.serializer",     StringSerializer.class.getName());
props.put("value.serializer",   StringSerializer.class.getName());
props.put("acks",               "all");          // ← el más importante
props.put("enable.idempotence", "true");

try (Producer<String,String> p = new KafkaProducer<>(props)) {
    p.send(new ProducerRecord<>(
        "pedidos-tiendamax",
        pedido.getOrderId(),       // ← key
        pedido.toJson()             // ← value
    ));
}

BLOQUE 5 · PASO 2
EL "PORQUÉ" DEL acks=all

3 niveles de garantía

ACKSQUIÉN CONFIRMARIESGO
0 Nadie. Fire & forget. Pérdida silenciosa
1 Solo el leader. Si el leader cae antes de replicar → pérdida
all Todas las ISR. Cero pérdida (con RF≥3)

En TiendaMax cada pedido = dinero. acks=all, sin excepciones.

BLOQUE 5 · PASO 2

La key decide la partición

key = order_id ORD-001 → hash → partición 0 ──┐ ORD-001 (pagado) → P0 │ orden garantizado ORD-001 (enviado) → P0 │ del ciclo de vida ORD-001 (entregado) → P0 ──┘ ORD-002 → hash → partición 2 ORD-003 → hash → partición 1

✓ key = order_id

Orden garantizado por pedido. Distribuye bien.

✗ key = cliente_id

Hotspot si "ana" hace el 80% de los pedidos.

BLOQUE 6 · PASO 3 DEMO

El loop del Consumer

while (running) {
    ConsumerRecords<String,String> records = consumer.poll(Duration.ofMillis(500));
    for (ConsumerRecord<String,String> r : records) {
        procesarPedido(r.value());        // ← lógica de negocio
    }
    consumer.commitSync();                 // ← commit DESPUÉS de procesar
}

Commit ANTES

at-most-once → pierdes mensajes si falla el procesar.

Commit DESPUÉS

at-least-once → puedes duplicar. Procesa idempotente.

BLOQUE 7 · PASO 4 DEMO

3 consumers, 3 particiones — RangeAssignor

topic: pedidos-tiendamax (3 particiones) group: servicio-inventario P0 ────→ consumer-A ✓ P1 ────→ consumer-B ✓ P2 ────→ consumer-C ✓ (consumer-D si lo agregas) ──→ IDLE / standby
  • Asignación 1:1 cuando #consumers ≤ #partitions.
  • Más consumers → los extras esperan a que muera otro.
  • Por eso elegimos 3 particiones desde el día 1.

BLOQUE 8 · PASO 5 DEMO

Anatomía de un rebalanceo

t=0s Ctrl+C en consumer-B 💥 t=10s group coordinator detecta heartbeat perdido (session.timeout.ms) t=11s PAUSE — todos los consumers paran de leer t=12s REASSIGN — P0,P2 a consumer-A · P1 a consumer-C t=13s RESUME — A y C siguen desde el ÚLTIMO offset commiteado (mensajes no commiteados se reprocessan → duplicados)

Por eso at-least-once + procesar idempotente.
