Exactly-Once
Semantics

Una de las preguntas más importantes en sistemas distribuidos es: ¿cuántas veces se procesa un mensaje? Kafka ofrece tres niveles de garantía, cada uno con sus trade-offs de rendimiento y complejidad. Entender cuál usar según tu caso de uso es una habilidad crítica de producción.

📨
At-Most-Once
El mensaje se envía una vez. Si hay un fallo antes del ACK, el mensaje se pierde. El producer no reintenta. Offset se confirma antes de procesar.
RIESGO: PÉRDIDA
📬
At-Least-Once
El producer reintenta en caso de fallo. El mensaje llegará mínimo una vez, pero puede llegar duplicado si el ACK se pierde. El consumer debe ser idempotente.
RIESGO: DUPLICADOS
🎯
Exactly-Once
El mensaje se procesa exactamente una vez. Requiere producers idempotentes + transacciones Kafka. Más lento, pero sin pérdidas ni duplicados. Es el estándar en fintech.
IDEAL: PRODUCCIÓN

Log Compaction

Por defecto, Kafka elimina mensajes después de que expira el tiempo de retención (log.retention.hours). Pero hay casos donde necesitas guardar siempre el último estado de cada entidad, sin importar cuándo ocurrió — como la dirección actual de un usuario o el saldo actual de una cuenta. Para esto existe Log Compaction.

Con compaction activado, Kafka garantiza que siempre habrá al menos el último mensaje de cada key en el log. Los mensajes más antiguos con la misma key son eliminados automáticamente por un proceso interno llamado log cleaner. Esto convierte a Kafka en algo similar a una base de datos key-value replicada y distribuida.

SIMULADOR · LOG COMPACTION
cleanup.policy=compact
ANTES DE COMPACTION — log completo
RESULTADO (aparecerá aquí)
⚠️
Tombstone: Para eliminar una key de un topic compactado, publicas un mensaje con esa key y value=null. Kafka mantiene ese "tombstone" durante un período (configurable con delete.retention.ms) antes de eliminarlo definitivamente. Esto garantiza que los consumers que están atrás en el log puedan ver que la key fue eliminada.
Topic compactado — configuración
# Crear topic con compaction via CLI kafka-topics.sh --create \ --topic user-profiles \ --partitions 6 \ --replication-factor 3 \ --config cleanup.policy=compact \ --config min.cleanable.dirty.ratio=0.1 \ --config segment.ms=3600000 // compactar segmentos cada 1 hora # Publicar un "tombstone" para eliminar la key user-42 kafka-console-producer.sh --topic user-profiles \ --property "parse.key=true" \ --property "key.separator=:" \ <<< "user-42:" # value vacío = tombstone

Kafka Streams

Hasta ahora hemos hablado de producers y consumers que simplemente mueven mensajes de A a B. Kafka Streams es una librería Java incluida en Kafka que te permite transformar, filtrar, agregar y enriquecer streams de datos en tiempo real — todo dentro de tu aplicación, sin necesidad de un cluster externo (como Spark o Flink).

🌊
KStream
Representa un flujo de eventos — cada registro es independiente. Como una lista infinita: pagos, clicks, mensajes. Cada evento importa por sí mismo.
APPEND-ONLY
📊
KTable
Representa el estado actual de algo — como una tabla de base de datos. Cada mensaje actualiza el valor de su key. Solo importa el último valor por key.
CHANGELOG
🏪
State Store
Almacén local (RocksDB) donde Streams guarda el estado de agregaciones, conteos o joins. Automáticamente respaldado en un topic compactado de Kafka.
LOCAL + REPLICADO
🔗
Stream Join
Combina dos streams o un stream con una tabla. Ejemplo: enriquecer un stream de pedidos con datos de usuario de una KTable, en tiempo real.

Integrar Kafka con bases de datos, data warehouses o servicios externos requiere código repetitivo y frágil. Kafka Connect es un framework para mover datos hacia y desde Kafka usando conectores preconstruidos, configurados con JSON — sin escribir código de producer/consumer.

Debezium — CDC con Kafka Connect: Es el conector más poderoso. Performance Tuning Lab

Kafka funciona bien out-of-the-box, pero en producción a alta escala, los parámetros de configuración marcan la diferencia entre 50K msg/s y 500K msg/s. Este laboratorio te permite ajustar los parámetros más impactantes y ver en tiempo real cómo afectan al throughput, la latencia y la seguridad.

⚡ PERFORMANCE LAB — PRODUCER
batch.size 16 KB
Tamaño máximo del lote de mensajes que el producer envía juntos. Mayor batch = mejor throughput, mayor latencia.
linger.ms 0 ms
Tiempo que el producer espera para acumular mensajes antes de enviar. 0 = envío inmediato. 5-20ms = mejor batching.
compression.type none
Algoritmo de compresión. none=sin overhead, snappy=balance, lz4=más rápido, zstd=mejor ratio.
acks 1
Confirmaciones requeridas. 0=sin espera (peligroso), 1=solo líder, all=todos los réplicas (más seguro, más lento).

CQRS · Event Sourcing
& Saga Pattern

Kafka no es solo un bus de mensajes — es la base sobre la que se construyen algunos de los patrones de arquitectura más poderosos en microservicios modernos. Estos tres patrones están profundamente interrelacionados y juntos resuelven los problemas más complejos de sistemas distribuidos.

✂️
CQRS
Command Query Responsibility Segregation. Separa las operaciones de escritura (Commands) de las de lectura (Queries) en modelos distintos. Los Commands publican eventos en Kafka. Las Queries leen de proyecciones optimizadas.
SEPARACIÓN LECTURA/ESCRITURA
📜
Event Sourcing
En lugar de guardar el estado actual en BD, guardas la secuencia de eventos que lo produjeron. El topic de Kafka IS la base de datos. Puedes reconstruir cualquier estado pasado reproduciendo el log.
EL LOG ES LA VERDAD
🎭
Saga Pattern
Coordina transacciones distribuidas entre múltiples microservicios usando eventos. Si un paso falla, se ejecutan "transacciones compensatorias" para deshacer los pasos previos. Sin Two-Phase Commit.

⚠️
Consistencia eventual vs ACID: El patrón Saga garantiza que el sistema eventualmente llega a un estado consistente, pero durante la ejecución puede haber inconsistencias temporales. En sistemas críticos como banca, esto requiere diseño cuidadoso — por ejemplo, reservar fondos (no debitar) hasta que todos los pasos confirmen.

Monitoring &
Consumer Lag

Un sistema Kafka en producción sin monitoreo es una bomba de tiempo. La métrica más importante a vigilar es el consumer lag — la diferencia entre el offset del último mensaje publicado y el último offset procesado por el consumer. Un lag creciente significa que tus consumers no están siguiendo el ritmo de los producers.

Quiz Experto

Estas preguntas van más allá de los conceptos básicos. Evalúan tu capacidad de tomar decisiones técnicas en escenarios reales de producción — el tipo de preguntas que aparecen en entrevistas para roles de arquitecto de software.

PREGUNTA 1 DE 8 MEDIO
Un producer tiene enable.idempotence=true pero NO configura transactional.id. ¿Qué garantía tiene realmente?
AExactly-once completo incluyendo el consumer
BNo habrá duplicados dentro de una sola sesión del producer, pero sin atomicidad multi-topic
CNada — idempotence sin transactional.id lanza excepción al iniciar
DLo mismo que transactional.id configurado, son equivalentes
Respuesta B. enable.idempotence=true activa un Producer ID (PID) y números de secuencia que el broker usa para deduplicar reintentos dentro de la misma sesión del producer. Esto elimina duplicados causados por reintentos de red. Sin embargo, no garantiza atomicidad entre múltiples topics/particiones ni visibilidad transaccional para los consumers. Para eso necesitas transactional.id + isolation.level=read_committed en el consumer.
PREGUNTA 2 DE 8DIFÍCIL
Tienes este código Kafka Streams. ¿Cuál es el problema potencial?
KStream<String, Order> orders = builder.stream("orders"); KTable<String, User> users = builder.table("users"); KStream<String, EnrichedOrder> enriched = orders .join(users, (order, user) -> enrich(order, user)); enriched.to("enriched-orders");
ANo se puede hacer join entre KStream y KTable en Kafka Streams
BSi la key del order no coincide con la key del user, el join retornará null silenciosamente
CEl join fallará porque KTable no soporta joins con streams en tiempo real
DEl código es correcto y no tiene problemas
Respuesta B. El join KStream-KTable en Kafka Streams es un left join basado en key. Si la key del stream de orders (ej: orderId) no coincide con la key de la KTable de users (ej: userId), el join producirá null para el user — y si tu función enrich() no maneja null, el stream fallará en runtime. La solución es hacer orders.selectKey((k, order) -> order.getUserId()) antes del join para re-keyear por userId.
PREGUNTA 3 DE 8DIFÍCIL
Tu consumer group tiene un lag creciente de 500K mensajes. Agregas 5 consumers más al grupo, pero el lag sigue creciendo. ¿Cuál es la causa más probable?
AHay un bug en el código del consumer que causa memory leak
BEl número de particiones del topic es menor que el número total de consumers activos
CEl broker está caído y no puede entregar mensajes
DKafka no permite agregar consumers a un grupo con lag activo
Respuesta B. Si el topic tiene, digamos, 3 particiones y ya tenías 3 consumers, agregar 5 más no ayuda — los 5 quedan IDLE. El paralelismo real está limitado por el número de particiones. La solución correcta es aumentar las particiones del topic (operación que requiere precaución en producción, ya que puede alterar el particionado por key) y luego agregar consumers. Regla: más consumers que particiones = consumers de sobra.
PREGUNTA 4 DE 8EXPERTO
¿Qué problema resuelve el patrón "Outbox Pattern" en sistemas con Kafka?
APermite a los consumers leer mensajes sin confirmación de offset automática
BOptimiza el uso de memoria del broker al comprimir mensajes antiguos
CGarantiza que los eventos se publiquen a Kafka solo si la transacción de BD local también fue exitosa
DPermite escalar particiones sin reiniciar el broker
Respuesta C. El Outbox Pattern resuelve el problema del "dual write": si guardas en BD Y publicas en Kafka en la misma operación, pueden desincronizarse si uno falla. La solución: en la misma transacción de BD, guardas el evento en una tabla outbox. Un proceso separado (o Debezium vía CDC) lee esa tabla y publica en Kafka. Así, publicar en Kafka solo ocurre si la transacción de BD fue exitosa. Es el patrón de oro para consistency en microservicios.
PREGUNTA 5 DE 8DIFÍCIL
Configuras cleanup.policy=compact en un topic. Un consumer reinicia desde el offset 0. ¿Qué mensajes verá?
ATodos los mensajes históricos desde el inicio del topic
BAl menos el último mensaje de cada key que existe actualmente, más mensajes recientes no compactados aún
CSolo los mensajes de las últimas 24 horas
DUn error — cleanup.policy=compact impide leer desde offset 0
Respuesta B. Con Log Compaction, el broker garantiza retener al menos el último mensaje de cada key — pero el compaction no ocurre instantáneamente. Los segmentos más nuevos aún no compactados tendrán múltiples versiones de una key. Un consumer leyendo desde el inicio verá: los valores más recientes de keys ya compactadas (solo el último) + todos los mensajes de segmentos recientes aún sin compactar. Esto hace al topic compactado ideal como fuente de verdad para reconstruir estado.
PREGUNTA 6 DE 8EXPERTO
En un Kafka Streams con state store, ¿dónde se almacena físicamente el estado y cómo sobrevive a un reinicio?
AEn memoria RAM del consumer — no sobrevive a reinicios
BEn una base de datos externa que debes configurar
CEn RocksDB local + un changelog topic en Kafka que permite reconstruir el store tras un reinicio
DEn ZooKeeper como coordinador de estado distribuido
Respuesta C. Kafka Streams usa RocksDB como motor de almacenamiento local en disco. Cada operación que modifica el state store también publica el cambio en un changelog topic interno en Kafka (con compaction activado). Al reiniciar una instancia, Streams restaura el RocksDB leyendo el changelog topic desde el principio — esto puede tardar si el estado es grande. Por eso en producción se usan standby replicas (num.standby.replicas) que mantienen copias calientes del state store.
PREGUNTA 7 DE 8DIFÍCIL
¿Cuál es la diferencia fundamental entre usar Kafka Connect vs escribir un consumer/producer manual para integrar Kafka con una base de datos externa?
AConnect es más rápido porque usa protocolos binarios propietarios
BConnect gestiona automáticamente offset tracking, escalado, reintentos, schemas y fault-tolerance — un consumer manual requiere implementar todo esto
CConnect solo funciona con bases de datos relacionales, no con NoSQL
DNo hay diferencia funcional, es solo preferencia del desarrollador
Respuesta B. Kafka Connect es un framework completo que maneja: tracking de offsets (qué se leyó ya), distribución de carga entre workers, reintentos automáticos en fallos, integración con Schema Registry para evolución de schemas, métricas JMX, REST API de administración, y transformaciones (SMT) sin código. Un consumer manual requiere implementar todo esto desde cero — lo cual es trabajo considerable y propenso a errores. Connect brilla especialmente con Debezium para CDC.
PREGUNTA 8 DE 8EXPERTO
En el patrón Saga con Kafka, el paso de pago falla. ¿Qué mecanismo garantiza que el pedido creado en el paso 1 sea revertido?
AKafka hace rollback automático usando transacciones Two-Phase Commit entre servicios
BEl payment-service publica un evento de fallo; el order-service lo consume y ejecuta su propia transacción compensatoria
CEl Saga orchestrator llama directamente via REST al order-service para cancelar
DKafka Streams detecta automáticamente el fallo y revierte los mensajes previos
Respuesta B. En el patrón Saga coreografiado con Kafka, no hay un coordinador central ni Two-Phase Commit (que no escala). Cada servicio escucha los eventos de los otros y reacciona. Si payment publica PaymentFailed, el order-service tiene un consumer que escucha ese evento y ejecuta su propia transacción compensatoria local (cancelar el pedido). Esta cadena de compensaciones se propaga hacia atrás. La clave: cada servicio es responsable de su propia compensación — diseño que escala horizontalmente sin coordinación centralizada.
