MÓDULO 09 · TUNING & PERFORMANCE
Tuning del Broker
NIVEL MEDIO

El rendimiento de un clúster Kafka no depende únicamente de cuántos brokers tengas o cuánta RAM haya en los servidores. Depende de cómo configures el sistema operativo, la JVM y los parámetros de red e I/O del broker. La mayoría de los problemas de performance que se atribuyen a Kafka en realidad son errores de configuración en el producer, el OS o el disco.

▶ ANALOGÍA · LA AUTOPISTA DE DATOS
Un broker Kafka es como una autopista de datos: agregar más carriles (threads) no soluciona el embotellamiento si el asfalto (disco) está roto. Antes de escalar horizontalmente, asegúrate de que cada broker individual esté correctamente afinado para el hardware que tiene.
🖥️
OS & Disco
vm.swappiness=1, transparent_hugepage=never, XFS sobre ext4. El broker Kafka es IO-bound, no CPU-bound. El sistema operativo gestiona el Page Cache — si el OS mueve ese cache al swap, la latencia se dispara.
☕
JVM Heap
Mantén el heap en 6–8 GB aunque el servidor tenga 64 GB. El resto lo usa el Page Cache del OS. Un heap de 32 GB en Kafka provoca GC pauses de varios segundos durante los cuales el broker deja de responder.
🌐
Red & Threads
num.io.threads=8, num.network.threads=3, socket.send.buffer.bytes=131072. Más threads no equivale a más throughput si el disco es el cuello de botella. Mide primero con iostat -x 1.

Parámetros clave de configuración del broker para producción:

PARÁMETRO DEFAULT RECOMENDACIÓN DESCRIPCIÓN
num.io.threads 8 num CPUs × 2 Threads para I/O de disco. Escalar si el disco no está saturado.
num.network.threads 3 num CPUs Threads para red (aceptar conexiones TCP de producers/consumers).
log.flush.interval.messages Long.MAX NO CAMBIAR Dejar que el OS gestione el flush. Cambiarlo a 1 destruye el throughput — fuerza fsync por cada mensaje.
socket.send.buffer.bytes 131072 1048576 Buffer de envío TCP por socket. Aumentar en redes de alta latencia (cross-datacenter).
replica.fetch.max.bytes 1048576 10485760 Tamaño máximo de fetch entre réplicas. Aumentar si tienes mensajes grandes.

Pensar que más heap = mejor rendimiento. Un heap de 32 GB en Kafka provoca GC pauses de varios segundos. Durante ese tiempo, el broker deja de responder completamente: los consumers reciben broker not available y los consumer groups hacen rebalance innecesario. Mantén el heap en 6–8 GB máximo, sin importar cuánta RAM tenga el servidor.

El 80% de los problemas de performance en Kafka no son del broker — son del producer. Ajusta linger.ms=20 y batch.size=65536 antes de tocar el broker. El efecto combinado de batching + compresión puede dar 10x throughput con el mismo hardware. Agrega compression.type=zstd para reducir I/O de disco y ancho de banda de red simultáneamente.

Benchmark completo del broker con herramientas nativas:

  • Ejecutar kafka-producer-perf-test.sh con acks=all, registrar baseline de throughput y latencia.
  • Ajustar linger.ms=20 y batch.size=65536 en el producer, ejecutar de nuevo y comparar.
  • Agregar compression.type=zstd y medir reducción en MB/s de escritura en disco.
  • Monitorear con iostat -x 1 durante el test: si %util > 90%, el disco es el cuello.
  • Ejecutar kafka-consumer-perf-test.sh y comparar throughput de lectura.

MÓDULO 10 · GOBERNANZA DE DATOS
Schema Registry
NIVEL MEDIO

En un sistema de microservicios con Kafka, los producers y consumers son equipos distintos que evolucionan de forma independiente. Si el producer cambia la estructura de sus mensajes sin avisar, los consumers fallan silenciosamente o, peor, procesan datos corruptos. El Schema Registry resuelve este problema estableciendo un contrato formal y versionado entre emisores y receptores.

▶ ANALOGÍA · EL CONTRATO DE API
El Schema Registry es como un contrato de API firmado entre equipos. El producer dice "mis datos tienen esta estructura", el Registry lo registra y versiona, y si el consumer recibe algo que no encaja — error en tiempo de compilación/serialización, no en producción. Es la diferencia entre un bug que aparece en el CD pipeline y uno que aparece a las 3 AM en producción.
schema-registry-architecture
Producer ──[schemaId(5 bytes) + bytes binarios Avro]──► Kafka Topic
    │                                                            │
    │  POST /subjects/pedidos-value/versions                     │  GET /schemas/ids/42
    ▼                                                            ▼
Schema Registry ◄──────────────────────────────────── Consumer
    │
    │  Almacena los schemas en:
    └─► _schemas (Kafka topic interno, factor replicación 3)

Flujo producer:
  1. Serializar objeto → Avro bytes
  2. Registrar/verificar schema en Registry → obtener schemaId (int32)
  3. Escribir: [0x00][schemaId 4 bytes][avro payload] → Kafka

Flujo consumer:
  1. Leer mensaje de Kafka
  2. Leer primer byte (magic byte = 0x00) + siguiente int32 = schemaId
  3. GET /schemas/ids/{schemaId} → obtener schema
  4. Deserializar Avro payload con ese schema

Kafka Schema Registry soporta 4 modos de compatibilidad de schemas. Elegir el modo correcto depende de si tienes control sobre los upgrades de producers y consumers:

MODO DESCRIPCIÓN CONSUMER NUEVO ← MSG VIEJO CONSUMER VIEJO ← MSG NUEVO USO RECOMENDADO
BACKWARD Consumer nuevo puede leer mensajes del producer viejo ✅ OK ❌ No garantizado Primero actualizar consumers, luego producers
FORWARD Consumer viejo puede leer mensajes del producer nuevo ❌ No garantizado ✅ OK Primero actualizar producers, luego consumers
FULL Ambas direcciones son compatibles ✅ OK ✅ OK Actualizaciones rolling sin coordinación
NONE Sin validación de compatibilidad ⚠️ Riesgo ⚠️ Riesgo Solo development / prototipado
💡
Reglas de cambio seguro (BACKWARD): Agregar campos nuevos con default = OK. Eliminar campos = BREAKING. Cambiar tipo de campo (int → string) = BREAKING. Renombrar campos = BREAKING (Avro usa posición y nombre).

Cambiar int → long pensando que es "compatible hacia arriba". Avro permite la sintaxis pero rompe la compatibilidad binaria: el wire format de un int y un long son diferentes (ZigZag encoding). El Schema Registry lo rechaza con INCOMPATIBLE si el modo es BACKWARD o FULL. La solución correcta siempre es agregar un campo nuevo en lugar de cambiar el tipo de uno existente.

La TopicNameStrategy (default) registra UN schema por topic. El subject name es {topic}-value. Si tienes múltiples tipos de evento en el mismo topic, usa RecordNameStrategy (subject = FQCN del record Avro) o TopicRecordNameStrategy. Mezclar dos Avro schemas distintos en el mismo topic con TopicNameStrategy es uno de los errores más comunes al migrar a Schema Registry — el segundo schema sobreescribe al primero y todos los consumers que lean mensajes viejos fallan en deserialización.

MÓDULO 11 · INTEGRACIÓN
Kafka Connect
NIVEL MEDIO

En arquitecturas reales, Kafka raramente existe de forma aislada. Necesita integrarse con bases de datos relacionales, data warehouses, sistemas de búsqueda, data lakes y decenas de otras fuentes y destinos de datos. Kafka Connect resuelve este problema con un framework declarativo: describes la integración en JSON y Connect gestiona los workers, el paralelismo y la tolerancia a fallos.

▶ ANALOGÍA · EL CARGADOR UNIVERSAL
Kafka Connect es como un cargador universal de datos. En vez de escribir código personalizado para leer MySQL y escribir en Elasticsearch, describes el conector en un archivo JSON y Connect lo hace automáticamente, con reintentos, dead-letter queues y exactly-once incluidos.
arquitectura-cdc-debezium
MySQL ──[Debezium Source Connector]──► Kafka ──[Elasticsearch Sink]──► Elasticsearch
  │       INSERT / UPDATE / DELETE          │         (indexación automática)
  │       capturado del binlog              │
  └──── binlog_row_image=FULL ──────────────┘

Kafka Connect Workers (distributed mode):
  ┌──────────────────────────────────────────────────────────┐
  │  Worker 1          Worker 2          Worker 3            │
  │  [Task 1-Source]   [Task 2-Source]   [Task 1-Sink]       │
  │  tabla: pedidos    tabla: clientes   index: pedidos       │
  └──────────────────────────────────────────────────────────┘
       │                   │                   │
       └───────────────────┴───────────────────┘
                Coordinación via Kafka topics internos:
                  connect-configs, connect-offsets, connect-status

Single Message Transforms (SMT) permiten transformar mensajes en el pipeline de Connect sin escribir código. El RegexRouter redirige mensajes a topics diferentes según el nombre del topic original:

JSON · SMT REGEXROUTER 
// Renombrar topics: tiendamax.tiendamax_db.clientes → cdc.clientes
"transforms": "dropPrefix",
"transforms.dropPrefix.type":
  "org.apache.kafka.connect.transforms.RegexRouter",
"transforms.dropPrefix.regex":
  "tiendamax\\.tiendamax_db\\.(.*)",
"transforms.dropPrefix.replacement": "cdc.$1"

// Resultado:
//   tiendamax.tiendamax_db.clientes  →  cdc.clientes
//   tiendamax.tiendamax_db.pedidos   →  cdc.pedidos
//
// Otros SMTs útiles:
//   ExtractField    → extraer un campo del envelope Debezium
//   InsertField     → agregar metadata (timestamp, topic name)
//   MaskField       → enmascarar PII (tarjetas, passwords)
//   Filter          → descartar mensajes según condición

No configurar snapshot.mode=initial o ignorar que Debezium requiere binlog_row_image=FULL en MySQL. Sin binlog_row_image=FULL, MySQL escribe en el binlog solo las columnas que cambian en un UPDATE, no el row completo. Resultado: el campo before del evento Debezium llega como null para todos los UPDATEs, haciendo imposible rastrear qué cambió. Configura en MySQL: SET GLOBAL binlog_row_image = 'FULL';

Un connector con tasks.max=3 NO crea 3 connectors — crea 3 tareas paralelas dentro del mismo connector. Para un Source Connector de Debezium, el número efectivo de tasks está limitado por el número de tablas monitoreadas. Para un Sink Connector, está limitado por el número de particiones del topic. Configurar tasks.max mayor que el límite real desperdicia recursos sin mejorar el throughput: las tasks extras se crean pero no procesan ninguna partición.

MÓDULO 12 · STREAM PROCESSING
Kafka Streams
NIVEL MEDIO

Kafka Streams es una librería de procesamiento de datos en tiempo real que corre dentro de tu propia aplicación JVM. No necesitas desplegar un cluster Flink, Spark Streaming ni ninguna infraestructura adicional. La librería consume mensajes del topic, aplica transformaciones stateless o stateful, y escribe resultados en otro topic — todo con garantías de exactly-once processing.

▶ ANALOGÍA · SQL EN TIEMPO REAL
Kafka Streams es como tener un SQL en tiempo real dentro de tu aplicación Java. No necesitas un cluster Flink ni Spark separado — es una librería que corre dentro de tu JVM y procesa los mensajes del topic a medida que llegan, con estado persistido localmente en RocksDB y replicado en Kafka.
topologia-kafka-streams
[pedidos-tiendamax] ──source──► filter(total > 500) ──► mapValues(enriquece)
                                                                      │
                           [pedidos-premium] ◄──sink── groupBy(categoria)
                                                                      │
                                                                 count(Tumbling 5min)
                                                                      │
                                                            [pedidos-por-cat-5m]

Procesadores internos (auto-generados por Kafka Streams DSL):
  KSTREAM-SOURCE-0000000000  (lee de pedidos-tiendamax)
  KSTREAM-FILTER-0000000001  (total > 500)
  KSTREAM-MAP-0000000002     (mapValues)
  KSTREAM-AGGREGATE-0000000003 (groupBy + count)
  STATE STORE: pedidos-KSTREAM-AGGREGATE-0000000003 (RocksDB local)
  Changelog topic: pedidos-app-KSTREAM-AGGREGATE-0000000003-changelog

La abstracción fundamental de Kafka Streams son tres tipos de streams con semánticas distintas:

TIPO SEMÁNTICA CARDINALIDAD ESTADO INTERNO CASO DE USO
KStream Stream de eventos. Cada record es un evento independiente. Infinita (append-only) Sin estado implícito Transacciones, logs, clics, métricas
KTable Tabla materializada del último valor por key (changelog stream). Finita por key RocksDB local + changelog topic Inventario actual, perfil de usuario, último precio
GlobalKTable Igual que KTable pero replicada en TODOS los nodos del clúster. Finita (debe caber en memoria) RocksDB en cada instancia Catálogos, tablas de referencia, lookups broadcast

Las operaciones de agregación sobre KStreams requieren definir una ventana temporal. Kafka Streams soporta tres tipos:

TUMBLING WINDOW
Ventanas fijas sin solapamiento. Cada evento pertenece exactamente a una ventana.

Ejemplo: contar pedidos cada 5 minutos. [0:00–5:00), [5:00–10:00)...

TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(5))
HOPPING WINDOW
Ventanas de tamaño fijo que se solapan. Un evento puede aparecer en N ventanas.

Ejemplo: ventana de 10 min que avanza cada 5 min. Un evento a 5:30 está en [0–10) y en [5–15).

TimeWindows.ofSizeAndGrace(Duration.ofMinutes(10), Duration.ofMinutes(5))
SESSION WINDOW
Ventanas delimitadas por inactividad. Tamaño variable — la ventana crece mientras lleguen eventos dentro del gap de inactividad.

Ejemplo: sesiones de usuario. Si no hay actividad en 30 min → nueva sesión.

SessionWindows.ofInactivityGapWithNoGrace(Duration.ofMinutes(30))
JAVA · KAFKA STREAMS DSL 
// Configuración básica
Properties props = new Properties();
props.put(StreamsConfig.APPLICATION_ID_CONFIG, "pedidos-app");
props.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(StreamsConfig.DEFAULT_KEY_SERDE_CLASS_CONFIG,
          Serdes.String().getClass());
props.put(StreamsConfig.DEFAULT_VALUE_SERDE_CLASS_CONFIG,
          Serdes.String().getClass());
// Exactly-once processing (requiere Kafka 2.5+)
props.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG,
          StreamsConfig.EXACTLY_ONCE_V2);

StreamsBuilder builder = new StreamsBuilder();

// Source: leer del topic de pedidos
KStream<String, Pedido> pedidos = builder.stream("pedidos-tiendamax");

// Filtrar pedidos premium (total > 500)
KStream<String, Pedido> premium = pedidos
  .filter((key, pedido) -> pedido.getTotal() > 500.0)
  .mapValues(pedido -> enriquecerConPuntos(pedido));

// Sink: escribir al topic de pedidos premium
premium.to("pedidos-premium");

// Aggregación: contar pedidos por categoría en ventana tumbling 5 min
KTable<Windowed<String>, Long> conteo = pedidos
  .groupBy((key, pedido) -> pedido.getCategoria())  // KGroupedStream
  .windowedBy(TimeWindows.ofSizeWithNoGrace(
      Duration.ofMinutes(5)))
  .count(Materialized.as("conteo-por-categoria"));  // State Store nombrado

// Serializar y escribir resultados
conteo.toStream()
  .map((windowed, count) -> KeyValue.pair(
      windowed.key() + "@" + windowed.window().start(),
      count.toString()))
  .to("pedidos-por-cat-5m");

KafkaStreams streams = new KafkaStreams(builder.build(), props);
streams.start();
Runtime.getRuntime().addShutdownHook(new Thread(streams::close));

Hacer un KStream.join(KStream, ...) sin .windowedBy(). Kafka Streams rechaza la compilación (o lanza excepción en runtime) porque los streams son infinitos: para hacer un join entre dos streams infinitos necesitas acotar el tiempo en el que dos eventos se consideran "relacionables". La API lo fuerza: stream1.join(stream2, joiner, JoinWindows.ofTimeDifferenceWithNoGrace(Duration.ofMinutes(5))). Para join sin ventana, usa KTable.join(KTable).

Los State Stores de Kafka Streams usan RocksDB por defecto. Cada store genera automáticamente un changelog topic interno (ej: pedidos-app-KSTREAM-AGGREGATE-STATE-STORE-0000000004-changelog). Si borras ese topic manualmente, el store se reconstruye relayendo todos los mensajes desde el inicio del topic fuente — puede tardar horas en producción con retención de días o semanas. Los changelogs también son la razón por la que el escalado horizontal de Kafka Streams requiere repartición: Kafka debe garantizar que todos los mensajes de la misma key vayan al mismo nodo que tiene el estado correspondiente.
