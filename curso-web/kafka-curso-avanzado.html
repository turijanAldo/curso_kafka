M13

Kafka Seguro

ANALOGÍA
Kafka sin seguridad es como una sala de servidores con la puerta abierta. Cualquiera con acceso a la red puede leer el topic de pagos o producir eventos falsos. SSL cierra la puerta, SASL pide el carnet de identidad, y las ACLs definen qué habitaciones puedes visitar.

Stack de Seguridad

🔐
SSL / TLS
Cifrado en tránsito entre brokers y clientes. Previene sniffing de paquetes. Usa certificados X.509, keystores y truststores gestionados con keytool. Configura ssl.endpoint.identification.algorithm=https para prevenir ataques MITM mediante verificación del hostname.
🪪
SASL
Autenticación (¿quién eres?). Mecanismos disponibles: PLAIN (usuario:password, solo con TLS), SCRAM-SHA-256/512 (hashing salted seguro), OAUTHBEARER (integración con OIDC/Keycloak). Importante: SASL no cifra — combinar siempre con SSL.
🚧
ACLs
Autorización (¿qué puedes hacer?). Por resource (topic, group, cluster, transactionalId) y operation (Read, Write, Create, Describe, Delete). Gestionadas con kafka-acls.sh. DENY-by-default cuando existe al menos una ACL.

Gestión de ACLs con kafka-acls.sh

kafka-acls.sh · SASL/SCRAM cluster
# Dar permiso de escritura a producer-app en topic pagos.* (prefixed)
kafka-acls.sh --bootstrap-server localhost:9092 \
  --add --allow-principal User:producer-app \
  --operation Write --topic pagos --resource-pattern-type prefixed

# Listar ACLs activas en el cluster
kafka-acls.sh --bootstrap-server localhost:9092 --list
Current ACLs for resource `Topic:PREFIXED:pagos`:
  User:producer-app has Allow permission for operations: Write

# Intentar violar la ACL desde consumer-app (debería fallar):
kafka-console-producer.sh --topic nominas \
  --bootstrap-server localhost:9092 \
  --producer.config producer-app.properties
[2024-01-15 10:23:41,234] ERROR Not authorized to access topics: [nominas]
  org.apache.kafka.common.errors.TopicAuthorizationException: AUTHORIZATION_FAILED

# Revocar permiso
kafka-acls.sh --bootstrap-server localhost:9092 \
  --remove --allow-principal User:producer-app \
  --operation Write --topic pagos --resource-pattern-type prefixed

Comparativa de Mecanismos SASL

MECANISMO ALMACENAMIENTO SEGURIDAD CASO DE USO
PLAIN Contraseñas en texto plano en server.properties Baja — requiere TLS obligatorio, expone creds sin TLS Solo dev/staging. Nunca producción sin TLS.
SCRAM-SHA-256 Hash salted en ZooKeeper o KRaft metadata Media-Alta — hash iterado con salt único por usuario Recomendado para la mayoría de despliegues on-premise.
SCRAM-SHA-512 Hash salted en ZK/KRaft (SHA-512) Alta — igual que 256 pero mayor resistencia brute-force Igual que SHA-256, mínima diferencia de performance (<1%).
OAUTHBEARER Tokens JWT efímeros — IdP externo Alta + rotación automática de tokens Enterprise: integra con Keycloak, Okta, Azure AD, LDAP.

Configurar allow.everyone.if.no.acl.found=true en producción "temporalmente" mientras se definen las ACLs reales. Kafka queda completamente abierto y no aparece ninguna advertencia visible en los logs normales. Sin ACLs + este flag activado = cualquier cliente en la red puede leer y escribir en cualquier topic.

Las ACLs en Kafka son DENY-by-default solo cuando hay al menos UNA ACL configurada en el cluster. Si allow.everyone.if.no.acl.found=true (default), sin ACLs = acceso total sin restricciones. El primer paso en cualquier hardening es añadir una ACL de negación explícita o cambiar este flag antes de añadir cualquier otra ACL. El orden importa: cambia el flag, luego añade ACLs permisivas.

Configuración server.properties (SASL/SCRAM)

server.properties 
# Listeners con SSL+SASL
listeners=SASL_SSL://0.0.0.0:9092
advertised.listeners=SASL_SSL://broker1.interno:9092
sasl.enabled.mechanisms=SCRAM-SHA-512
sasl.mechanism.inter.broker.protocol=SCRAM-SHA-512
security.inter.broker.protocol=SASL_SSL

# SSL — keystores
ssl.keystore.location=/etc/kafka/ssl/broker.keystore.jks
ssl.keystore.password=changeit
ssl.truststore.location=/etc/kafka/ssl/broker.truststore.jks
ssl.truststore.password=changeit
ssl.endpoint.identification.algorithm=https

# Autorización — ACLs DENY-by-default
authorizer.class.name=kafka.security.authorizer.AclAuthorizer
allow.everyone.if.no.acl.found=false
super.users=User:admin;User:kafka-broker

Multi-Región & DR

ANALOGÍA
MirrorMaker 2 es como un servicio de mensajería express entre dos ciudades (data centers). Cuando envías algo en Nueva York, MM2 lo entrega automáticamente en Los Ángeles. Si el DHL de NY colapsa, el de LA ya tiene todo listo — solo necesitas redirigir el tráfico.

Arquitectura MirrorMaker 2

MirrorMaker 2 — topología activo-pasivo
cluster-us (primary) cluster-eu (secondary) ┌──────────────────────┐ ┌──────────────────────┐ │ pagos.pedidos │──MM2──► │ us.pagos.pedidos │ │ pagos.usuarios │──MM2──► │ us.pagos.usuarios │ │ pagos.eventos │──MM2──► │ us.pagos.eventos │ │ │ │ │ │ producers → aquí │ │ consumers → aquí │ │ (normal) │ │ (en failover) │ └──────────────────────┘ └──────────────────────┘ ↑ ACTIVO ↑ STANDBY │ │ └─────────── MM2 lag ─────────────┘ (replication lag = RPO)

RPO y RTO

⏱️
RPO — Recovery Point Objective
Cuántos datos puedes perder medido en tiempo. Con MM2, depende del replication lag. Si el lag es 5s → RPO ≤ 5s. En activo-pasivo, algo de lag es inevitable por la latencia de red entre regiones. Monitorea el lag de MM2 como SLO crítico: kafka.connect:type=mirror-source-connector-metrics,target-alias=*.
🏃
RTO — Recovery Time Objective
Cuánto tiempo tarda en recuperarse el servicio tras una caída. Con MM2 + offset sync activado, el failover de consumer groups puede ser <1 minuto. Sin offset sync, los consumers reprocesarán desde el inicio o desde auto.offset.reset=earliest. La herramienta MirrorCheckpointConnector es la clave del offset mapping.

Estrategias de Disaster Recovery

ESTRATEGIA COMPLEJIDAD RTO RPO TRADE-OFFS
Activo-Pasivo Baja — MM2 unidireccional ~1-5 min con offset sync Segundos (lag de MM2) Simple, sin conflictos de offsets. Capacidad standby infrautilizada.
Activo-Activo Alta — MM2 bidireccional <30s (ya hay consumers en ambos) Casi cero (ambos clusters activos) Conflictos de offsets. Requiere topic naming convention con prefijos de región.
Stretch Cluster (multi-DC RAFT) Media — misma admin, múltiples AZs Transparente (mismo cluster) Cero (mismo cluster) Solo viable entre AZs (<10ms). Con >100ms entre regiones → problemas de ISR y reelecciones.

Configuración MirrorMaker 2

mm2.properties — activo-pasivo US → EU 
# Clusters participantes
clusters = cluster-us, cluster-eu

cluster-us.bootstrap.servers = us-broker1:9092,us-broker2:9092
cluster-eu.bootstrap.servers = eu-broker1:9092,eu-broker2:9092

# Replicación US → EU (unidireccional)
cluster-us->cluster-eu.enabled = true
cluster-us->cluster-eu.topics = pagos\.*
cluster-us->cluster-eu.groups = .*

# Offset sync para failover limpio (RTO bajo)
checkpoints.topic.replication.factor = 3
emit.checkpoints.enabled = true
emit.checkpoints.interval.seconds = 5
sync.group.offsets.enabled = true
sync.group.offsets.interval.seconds = 5

# Topics internos de MM2 (NO borrar)
# mm2-offset-syncs.cluster-us.internal
# mm2-configs.cluster-us.internal
# heartbeats

Usar MirrorMaker 1 en 2025. MM1 no preserva offsets ni replica los topics internos (__consumer_offsets). Al hacer failover, los consumers recomienzan desde auto.offset.reset=earliest — reprocesando potencialmente millones de eventos. MM2 resuelve esto con MirrorCheckpointConnector que traduce offsets entre clusters.

MM2 genera automáticamente topics internos: heartbeats, mm2-offset-syncs.cluster-us.internal, mm2-configs.cluster-us.internal. NUNCA borres estos topics manualmente — MM2 pierde el track de los offsets traducidos y el failover falla silenciosamente. El consumer group en el cluster de destino arranca desde el inicio sin ningún error obvio en los logs de la aplicación.

Objetivo: Dos clusters Docker (cluster-us, cluster-eu). MirrorMaker 2 replicando pagos.* de US→EU.

  • Producir 1000 mensajes en cluster-us:pagos.pedidos
  • Verificar llegada en cluster-eu:us.pagos.pedidos con offset mapeado
  • Activar sync.group.offsets.enabled=true y confirmar offset mapping con MirrorCheckpointConnector
  • Simular caída de cluster-us (docker stop)
  • Failover del consumer group a cluster-eu — verificar que no hay reprocesamiento

Troubleshoot & Recovery

ANALOGÍA
El troubleshooting de Kafka es como diagnóstico médico de emergencia. No puedes hacer biopsia (parar el cluster) — tienes que diagnosticar con el paciente en pie, interpretando síntomas (logs, métricas) y aplicando tratamiento (reasignación, ajuste de config) sin detener el servicio.

Runbook de Incidentes Críticos

📈
LAG Exponencial
1. ¿Consumer processing time > max.poll.interval.ms? → Aumentar o reducir max.poll.records.

2. ¿Disk I/O del broker al 100%? → Añadir broker o reasignar particiones.

3. ¿GC pause prolongado en consumer? → Reducir heap o migrar a G1GC/ZGC.
🔇
Under-Replicated Partitions
1. kafka-topics.sh --describe --under-replicated-partitions para identificar.

2. ¿Broker follower lento? → Revisar network entre brokers (replica.lag.time.max.ms).

3. ¿Disco lleno? → Limpiar logs antiguos, reducir log.retention.bytes.

4. Ejecutar kafka-reassign-partitions.sh para mover particiones a brokers sanos.
💥
NotEnoughReplicasException
Causa: min.insync.replicas=2 pero el ISR tiene solo 1 replica (broker caído). Producer con acks=all rechazado con excepción.

Fix inmediato: Recuperar el broker caído.

Fix temporal (riesgoso): Reducir min.insync.replicas=1 hasta recuperar el broker. Documenta y revierte.

Árbol de Decisión — LAG Creciente

troubleshoot-lag.sh · árbol de decisión
LAG creciendo en kafka-consumer-groups.sh │ ├─► ¿consumer processing time > max.poll.interval.ms? │ │ │ └─ SÍ → reduce max.poll.records (menos batch) │ o aumenta max.poll.interval.ms (más tiempo) │ o optimiza lógica de negocio del consumer │ ├─► ¿consumer rebalanceando frecuentemente? │ │ │ └─ SÍ → aumenta session.timeout.ms y heartbeat.interval.ms │ revisa GC pause del consumer (jstat -gcutil <pid>) │ considera static membership (group.instance.id) │ ├─► ¿producer throughput muy alto vs particiones? │ │ │ └─ SÍ → añade particiones al topic │ escala consumers hasta = nº particiones │ verifica que no hay consumer ocioso │ └─► ¿broker disk I/O al tope? │ └─ SÍ → añade broker nuevo reasigna particiones calientes revisa segment.bytes y flush config

Archivos de Log Clave

ARCHIVO RUTA DEFAULT QUÉ BUSCAR
server.log /var/log/kafka/server.log Arranque/parada, liderazgo de particiones, errores de disco, excepciones de replicación. El log más importante para diagnóstico general.
controller.log /var/log/kafka/controller.log Elecciones de líder, cambios en ISR, eventos KRaft. Clave cuando hay elecciones frecuentes o broker bouncing.
state-change.log /var/log/kafka/state-change.log Transiciones de estado de particiones y réplicas. Útil para rastrear cuándo una partición perdió el ISR y cuándo lo recuperó.
kafka-authorizer.log /var/log/kafka/kafka-authorizer.log Todos los intentos de acceso: ALLOWED y DENIED. Esencial para debuggear ACLs y auditoría de seguridad. Puede ser muy verboso — usar con log4j filtering.

Reasignación de Particiones

kafka-reassign-partitions.sh · broker enfermo → sano
# 1. Generar plan de reasignación (broker 3 está enfermo, mover a broker 4)
kafka-reassign-partitions.sh --bootstrap-server localhost:9092 \
  --generate --topics-to-move-json-file topics.json \
  --broker-list "1,2,4"

# 2. Ejecutar reasignación (guardar salida como reassignment.json)
kafka-reassign-partitions.sh --bootstrap-server localhost:9092 \
  --execute --reassignment-json-file reassignment.json \
  --throttle 50000000 # 50 MB/s — no saturar red

# 3. Verificar progreso (puede tardar minutos)
kafka-reassign-partitions.sh --bootstrap-server localhost:9092 \
  --verify --reassignment-json-file reassignment.json
Status of partition reassignment:
Reassignment of partition pagos.pedidos-0 is completed
Reassignment of partition pagos.pedidos-1 is still in progress

Ejecutar kafka-leader-election.sh --election-type UNCLEAN para recuperar disponibilidad rápidamente durante una incidencia. Una elección UNCLEAN puede elegir un líder que no estaba en el ISR → pérdida de datos permanente e irrecuperable. Los mensajes producidos con acks=all que estaban en el líder anterior pero no en el follower elegido se pierden para siempre. Solo usar UNCLEAN election cuando los datos ya están perdidos y la disponibilidad es prioritaria.

El 90% de los "problemas de Kafka" a las 3 AM son en realidad problemas de consumer. Antes de tocar el broker, ejecuta kafka-consumer-groups.sh --describe --group tu-grupo y mira el LAG por partición. Si el LAG creció en una sola partición → problema del consumer asignado a esa partición, no del broker. Si el LAG creció uniformemente en todas las particiones → entonces investiga el broker o el producer throughput.

Chaos Engineering Lab: Diagnóstico y recuperación de broker enfermo.

  • Llenar disco de un broker con dd if=/dev/zero of=/var/lib/kafka/fill bs=1M count=2048
  • Observar ISR shrink en state-change.log y under-replicated partitions
  • Recuperar borrando segmentos de log antiguos con kafka-delete-records.sh
  • Ejecutar reasignación de particiones con throttle configurado
  • Verificar recuperación completa del ISR — todas las particiones fully replicated

Kafka en Kubernetes

ANALOGÍA
Desplegar Kafka en Kubernetes sin un Operator es como construir una casa sin planos — funciona, pero se cae en el primer terremoto. El Operator de Strimzi es el arquitecto que sabe exactamente cómo colocar cada pieza: anti-affinity, PVCs, rolling updates, y ACLs automáticas.

Arquitectura Strimzi

☸️
Strimzi Operator
Gestiona el lifecycle completo de Kafka via CRDs de Kubernetes. Recursos: Kafka, KafkaTopic, KafkaUser, KafkaMirrorMaker2. Soporta rolling updates sin downtime, gestión automática de server.properties, y reconciliación continua del estado deseado.
💾
Storage en Kubernetes
Local PVs (NVMe hostPath): Mejor latencia y throughput, pero el pod queda atado al nodo. Network storage (EBS, GCE PD): Mayor flexibilidad (pod migra), pero +10-30% latencia. Usa PodDisruptionBudget para garantizar que rolling updates no dejan ISR por debajo de min.insync.replicas.
☁️
Confluent Cloud — Costos Ocultos
Serverless tiers (Basic/Standard) vs Dedicated. El costo principal no son las instancias sino el egress de red entre AZs. En AWS, datos replicados entre AZs = $0.01/GB. Con RF=3 y 3 AZs, cada byte escrito genera 2 bytes de egress. A 100 MB/s = ~$500/mes solo en egress inter-AZ.

Strimzi CRD — Kafka Cluster

kafka-cluster.yaml · Strimzi CRD 
apiVersion: kafka.strimzi.io/v1beta2
kind: Kafka
metadata:
  name: kafka-produccion
  namespace: kafka
spec:
  kafka:
    replicas: 3
    version: 3.7.0
    listeners:
      - name: tls
        port: 9093
        type: internal
        tls: true
        authentication:
          type: scram-sha-512
    authorization:
      type: simple           # AclAuthorizer
    config:
      offsets.topic.replication.factor: 3
      transaction.state.log.replication.factor: 3
      transaction.state.log.min.isr: 2
      min.insync.replicas: 2
      allow.everyone.if.no.acl.found: false
    storage:
      type: jbod
      volumes:
        - id: 0
          type: persistent-claim
          size: 500Gi
          class: fast-local-nvme
          deleteClaim: false
        # Anti-affinity automático en Strimzi — nunca 2 brokers en mismo nodo
    template:
      pod:
        affinity:
          podAntiAffinity:
            requiredDuringSchedulingIgnoredDuringExecution:
              - labelSelector:
                  matchLabels:
                    strimzi.io/name: kafka-produccion-kafka
                topologyKey: kubernetes.io/hostname
---
apiVersion: kafka.strimzi.io/v1beta2
kind: KafkaUser
metadata:
  name: producer-app
  labels:
    strimzi.io/cluster: kafka-produccion
spec:
  authentication:
    type: scram-sha-512   # Strimzi genera y rota el secret
  authorization:
    type: simple
    acls:
      - resource:
          type: topic
          name: pagos
          patternType: prefix
        operations: [Write, Describe, Create]

💡 El egress de red inter-AZ es el costo oculto más frecuente. Con RF=3 y 3 AZs, cada byte escrito genera 2 bytes de replicación entre AZs. A 100 MB/s sostenidos eso son ~18 TB/mes de egress = ~$175-500/mes solo en transferencia, según proveedor cloud.

Usar EBS gp3 multi-AZ como storage principal para logs de Kafka en producción. El throughput de EBS tiene burst limits variables (hasta 1000 MB/s en burst, pero baseline mucho menor). Durante rebalanceo o Kafka Streams rekeying, el spike de I/O activa el throttling de EBS y el broker se vuelve lento durante minutos, causando ISR shrink en cascada. Prefiere local NVMe con hostPath o local PersistentVolumes.

En Kubernetes, NUNCA pongas dos brokers Kafka en el mismo nodo físico. Usa podAntiAffinity con requiredDuringSchedulingIgnoredDuringExecution (no preferred — required). Si no, cuando el nodo falla, pierdes 2 de 3 brokers → min.insync.replicas=2 falla → cluster no acepta writes. Strimzi configura esto automáticamente en su Helm chart, pero verifica siempre con kubectl get pods -o wide que ningún nodo tiene dos brokers.

PodDisruptionBudget — Protección durante Rolling Updates

pdb.yaml · PodDisruptionBudget para Kafka 
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: kafka-pdb
  namespace: kafka
spec:
  maxUnavailable: 1   # Máximo 1 broker down a la vez
  selector:
    matchLabels:
      strimzi.io/name: kafka-produccion-kafka

# Con RF=3 y min.insync.replicas=2:
# maxUnavailable=1 garantiza que siempre hay 2 brokers en ISR
# durante kubectl drain o node upgrades del cluster K8s
# Strimzi genera este PDB automáticamente — verificar que existe
