MÓDULO 01 · EL PROBLEMA
¿Por qué el testing Kafka
es diferente?

Testear una API REST es simple: envías un HTTP request y verificas la respuesta. Synchronous, determinístico, inmediato. El testing de microservicios Kafka es fundamentalmente diferente porque el procesamiento es asíncrono, distribuido y basado en eventos que viajan entre servicios independientes.

▶ ANALOGÍA · EL JUEGO DEL TELÉFONO
Imagina testear un juego del teléfono con 4 jugadores. El jugador 1 susurra un mensaje. Quieres verificar que el jugador 4 recibió el mensaje correcto. ¿Cuándo preguntas al jugador 4? Si preguntas demasiado pronto, todavía no lo recibió. Si esperas demasiado, el test tarda minutos. Y si un jugador intermedio se equivoca, ¿cómo aislas el error?

Eso es exactamente el reto de testear un Choreography-based Saga con 4 microservicios y 6 topics Kafka.

Los 4 desafíos únicos del testing Kafka

⏱️
Asincronía
El producer publica y retorna inmediatamente. El consumer procesa en otro hilo, quizás millisegundos después, quizás segundos. ¿Cuánto espera tu test? ¿Thread.sleep(3000)? Eso es un antipatrón: flaky en CI, lento en local.
🌐
Infraestructura real
A diferencia de una BD en memoria (H2), Kafka no tiene una versión "lightweight" nativa. Necesitas un broker real o una solución de test que lo emule. Esto afecta el tiempo de arranque de cada test.
🔗
Acoplamiento de servicios
En un Saga, el resultado de un test depende de que N servicios estén corriendo. Si quieres testear solo account-service, ¿arrancas validation-service también? ¿O mocks?
🔄
Estado compartido
Kafka retiene mensajes. Si un test publica en transfer.requested y el siguiente test arranca sin limpiar, el consumer del segundo test puede recibir mensajes del primero. El orden importa.

La trampa más común: usar Thread.sleep() para esperar que el consumer procese el mensaje.

Esto hace los tests lentos (porque siempre esperan el tiempo máximo) y flaky (porque en un servidor CI lento, 3 segundos no son suficientes). La solución correcta: un mecanismo de polling con timeout — como el que provee Awaitility.

anti-patrón vs. patrón correcto
// ❌ ANTI-PATRÓN: Thread.sleep() fijo producer.send(event); Thread.sleep(3000); // ¿y si CI tarda 5 segundos? assertThat(repository.count()).isEqualTo(1); // ✅ PATRÓN CORRECTO: Awaitility con polling producer.send(event); await().atMost(10, SECONDS) .pollInterval(200, MILLISECONDS) .until(() -> repository.count() == 1); assertThat(repository.findAll()).hasSize(1); // Awaitility: reintenta la condición hasta que sea true o pase el timeout. // El test termina tan pronto como el consumer procesa — sin espera innecesaria.

En producción, el testing de sistemas Kafka es tan importante como el código en sí. Netflix, Uber y LinkedIn (quien creó Kafka) tienen frameworks internos de testing dedicados. La razón: un bug en el consumer que procesa pagos que solo se detecta en producción puede costar millones. El costo de escribir el test es marginal comparado.

Una regla práctica: por cada consumer que escribes, escribe al menos un test de integración que verifique el flujo completo: publicar el mensaje → esperar el procesamiento → verificar el estado en DB.

MÓDULO 02 · ESTRATEGIA
La pirámide de tests
para microservicios Kafka

La pirámide de testing clásica (unit → integration → e2e) aplica a Kafka, pero con una variante importante: la capa de integración se divide en dos subcapas según si usamos Kafka simulado (@EmbeddedKafka) o Kafka real en contenedor (Testcontainers).

🌐
E2E — End to End (Testcontainers multi-servicio)
Arranca todos los servicios. Envía un POST. Verifica el estado final. Lento (30s+), pero verifica la integración real entre servicios. Pocos tests, solo los flujos críticos.
~30s / test
⚙️
Integración — Testcontainers (Kafka + DB real en contenedor)
Un servicio. Kafka y MySQL reales en Docker. Verifica consumer con DB real. Sin mocks de infraestructura. Detecta problemas de serialización, queries JPA y transacciones reales.
~5-10s / test
🔌
Integración — @EmbeddedKafka (Kafka en memoria)
Un servicio. Kafka en memoria (sin Docker). Verifica consumer con DB de test. Más rápido que Testcontainers, suficiente para la mayoría de casos. Ideal para CI/CD frecuente.
~1-3s / test
⚡
Unitario — Mockito (sin Kafka, sin DB)
Testea la lógica del service (ValidationService, DebitService) de forma aislada. Mock del producer, mock del repository. Verifica reglas de negocio puras. Muy rápido, muy numerosos.
<100ms / test
Característica Unitario @EmbeddedKafka Testcontainers E2E
Kafka real No Emulado Sí (Docker) Sí (Docker)
DB real No (mock) H2 / real MySQL real MySQL real
Velocidad <100ms 1–3s 5–10s 30s+

💡
Regla práctica para este lab: 70% unitarios (lógica de negocio), 25% @EmbeddedKafka o Testcontainers (flujos del consumer), 5% E2E (el Saga completo). No necesitas Testcontainers para cada cosa — @EmbeddedKafka cubre la mayoría de los casos.

MÓDULO 03 · CAPA 1
Tests unitarios
con Mockito

Los tests unitarios verifican la lógica de negocio pura sin depender de Kafka, DB ni ninguna infraestructura. Son los más fáciles de escribir, los más rápidos y los que más deberías tener. La clave: aislar la clase bajo test mockeando sus dependencias.

Testear ValidationService

La regla más importante: testea comportamiento, no implementación. No testees que se llamó a repository.findById() — testea que cuando la cuenta no existe, se publica un evento FAILED con el mensaje correcto.

JAVA · ValidationServiceTest.java 
@ExtendWith(MockitoExtension.class)
class ValidationServiceTest {

    @Mock  AccountRepository       accountRepository;
    @Mock  ValidationEventProducer producer;
    @InjectMocks ValidationService validationService;

    // ── Dato de prueba compartido ──────────────────────────────────────────
    private TransferRequestedEvent evento(String from, String to, double amount) {
        return TransferRequestedEvent.builder()
                .transactionId("tx-001")
                .fromAccount(from).toAccount(to)
                .amount(BigDecimal.valueOf(amount))
                .timestamp(Instant.now())
                .build();
    }

    // ── CASO FELIZ ─────────────────────────────────────────────────────────
    @Test
    @DisplayName("Publica VALIDATED cuando ambas cuentas existen y el monto es positivo")
    void validacion_exitosa() {
        // GIVEN — ambas cuentas existen en la DB
        given(accountRepository.existsById("ACC-001")).willReturn(true);
        given(accountRepository.existsById("ACC-002")).willReturn(true);

        // WHEN — el servicio valida el evento
        validationService.validate(evento("ACC-001", "ACC-002", 100.0));

        // THEN — se publicó exactamente un VALIDATED y cero FAILED
        then(producer).should(times(1)).publishValidated(any());
        then(producer).should(never()).publishFailed(any(), anyString(), anyString());
    }

    // ── CUENTA DESTINO INEXISTENTE ─────────────────────────────────────────
    @Test
    @DisplayName("Publica FAILED con razón correcta cuando la cuenta destino no existe")
    void cuenta_destino_inexistente() {
        // GIVEN
        given(accountRepository.existsById("ACC-001")).willReturn(true);
        given(accountRepository.existsById("ACC-999")).willReturn(false);

        // WHEN
        validationService.validate(evento("ACC-001", "ACC-999", 50.0));

        // THEN — FAILED publicado con mensaje que menciona la cuenta correcta
        ArgumentCaptor<String> reasonCaptor = ArgumentCaptor.forClass(String.class);
        then(producer).should().publishFailed(any(), reasonCaptor.capture(), anyString());
        assertThat(reasonCaptor.getValue()).contains("ACC-999");
        then(producer).should(never()).publishValidated(any());
    }

    // ── MISMA CUENTA ORIGEN Y DESTINO ──────────────────────────────────────
    @Test
    @DisplayName("Publica FAILED cuando origen y destino son la misma cuenta")
    void misma_cuenta() {
        validationService.validate(evento("ACC-001", "ACC-001", 10.0));
        // Fail-fast: ni siquiera debería consultar la DB
        then(accountRepository).should(never()).existsById(any());
        then(producer).should().publishFailed(any(), contains("misma"), anyString());
    }

    // ── MONTO CERO ─────────────────────────────────────────────────────────
    @Test
    @DisplayName("Publica FAILED cuando el monto es cero o negativo")
    void monto_invalido() {
        validationService.validate(evento("ACC-001", "ACC-002", 0.0));
        then(producer).should().publishFailed(any(), contains("monto"), anyString());
    }
}
🔍
BDD style (Given / When / Then): usar given() y then() de BDDMockito en lugar de when() y verify() hace los tests mucho más legibles. El nombre del método del test debe describir el comportamiento esperado, no el método que se llama.

Testear DebitService — lógica financiera

JAVA · DebitServiceTest.java 
@ExtendWith(MockitoExtension.class)
class DebitServiceTest {

    @Mock  AccountRepository accountRepository;
    @InjectMocks DebitService debitService;

    private Account cuenta(String id, double saldo) {
        Account a = new Account();
        a.setId(id); a.setBalance(BigDecimal.valueOf(saldo)); a.setVersion(0L);
        return a;
    }

    @Test
    @DisplayName("Debita correctamente y retorna el saldo actualizado")
    void debito_exitoso() {
        Account cuentaAna = cuenta("ACC-001", 1000.0);
        given(accountRepository.findById("ACC-001")).willReturn(Optional.of(cuentaAna));
        given(accountRepository.save(any())).willAnswer(inv -> inv.getArgument(0));

        Account resultado = debitService.debit("ACC-001", BigDecimal.valueOf(300.0));

        assertThat(resultado.getBalance()).isEqualByComparingTo("700.00");
        // Verifica que save() fue llamado con la cuenta con saldo actualizado
        then(accountRepository).should().save(argThat(a ->
                a.getBalance().compareTo(BigDecimal.valueOf(700.0)) == 0));
    }

    @Test
    @DisplayName("Lanza InsufficientFundsException cuando el saldo es insuficiente")
    void saldo_insuficiente() {
        given(accountRepository.findById("ACC-002"))
                .willReturn(Optional.of(cuenta("ACC-002", 100.0)));

        assertThatThrownBy(() -> debitService.debit("ACC-002", BigDecimal.valueOf(500.0)))
                .isInstanceOf(DebitService.InsufficientFundsException.class)
                .hasMessageContaining("Disponible: 100");

        // El save() NUNCA debe llamarse si el saldo es insuficiente
        then(accountRepository).should(never()).save(any());
    }

    @Test
    @DisplayName("Lanza AccountNotFoundException cuando la cuenta no existe")
    void cuenta_inexistente() {
        given(accountRepository.findById(anyString())).willReturn(Optional.empty());

        assertThatThrownBy(() -> debitService.debit("ACC-999", BigDecimal.ONE))
                .isInstanceOf(DebitService.AccountNotFoundException.class);
    }

    @Test
    @DisplayName("Usa BigDecimal — no hay error de punto flotante con 0.1 + 0.2")
    void precision_bigdecimal() {
        // Este test falla si alguien cambia BigDecimal por double
        given(accountRepository.findById(any())).willReturn(Optional.of(cuenta("X", 0.3)));
        given(accountRepository.save(any())).willAnswer(inv -> inv.getArgument(0));

        Account r = debitService.debit("X", BigDecimal.valueOf(0.1));
        assertThat(r.getBalance()).isEqualByComparingTo("0.20"); // no 0.19999999...
    }
}

El test de BigDecimal parece trivial, pero es fundamental. Si en el futuro alguien "optimiza" cambiando BigDecimal por double para ahorrarse tipado, este test fallará inmediatamente. Los tests son documentación ejecutable de las decisiones de diseño — incluyendo las que parecen obvias.

MÓDULO 04 · CAPA 2A
@EmbeddedKafka
Kafka en memoria

@EmbeddedKafka levanta un broker Kafka real en la JVM, sin Docker, sin contenedores. Es parte de spring-kafka-test — la misma dependencia que ya usas para los tests de Spring. Ideal para verificar el flujo completo publicar → consumer → DB en menos de 3 segundos.

▶ ANALOGÍA · EL SIMULADOR DE VUELO
@EmbeddedKafka es como un simulador de vuelo: no es un avión real, pero tiene todos los controles y reacciona igual que uno para la mayoría de situaciones. Suficiente para entrenar pilotos (verificar consumers) sin el costo de usar el avión real (Docker, CI más lento).

Test de integración del TransferRequestedConsumer

JAVA · TransferRequestedConsumerIT.java 
@SpringBootTest                              // levanta el contexto completo
@EmbeddedKafka(
    partitions = 1,
    topics = { "transfer.requested", "transfer.validated", "transfer.failed" }
)
@TestPropertySource(properties = {
    // Redirige el consumer/producer al broker embebido
    "spring.kafka.bootstrap-servers=${spring.embedded.kafka.brokers}",
    // earliest para que el consumer lea los mensajes del test
    "spring.kafka.consumer.properties.auto.offset.reset=earliest"
})
class TransferRequestedConsumerIT {

    @Autowired KafkaTemplate<String, Object> kafkaTemplate;
    @Autowired ProcessedEventRepository  processedEventRepo;

    // Spy del producer real para verificar qué publicó
    @SpyBean ValidationEventProducer producer;

    @BeforeEach
    void limpiar() {
        processedEventRepo.deleteAll(); // estado limpio entre tests
    }

    @Test
    @DisplayName("Publica VALIDATED cuando ambas cuentas existen")
    void flujo_feliz() {
        TransferRequestedEvent evento = TransferRequestedEvent.builder()
                .transactionId(UUID.randomUUID().toString())
                .fromAccount("ACC-001").toAccount("ACC-002")
                .amount(BigDecimal.valueOf(100))
                .timestamp(Instant.now())
                .build();

        // ACT — publicar el evento en Kafka embebido
        kafkaTemplate.send("transfer.requested", evento.getFromAccount(), evento);

        // ASSERT — esperar hasta 10s a que el consumer procese
        await().atMost(10, SECONDS)
               .pollInterval(200, MILLISECONDS)
               .untilAsserted(() -> {
                   // El evento quedó registrado en processed_events
                   assertThat(processedEventRepo.existsByEventKeyAndServiceName(
                           evento.getTransactionId() + ":TRANSFER_REQUESTED",
                           "validation-service"
                   )).isTrue();
                   // El producer publicó exactamente un VALIDATED
                   then(producer).should(times(1)).publishValidated(any());
               });
    }

    @Test
    @DisplayName("No reprocesa un evento duplicado — idempotencia Capa 2")
    void idempotencia_duplicado() {
        var txId = UUID.randomUUID().toString();
        var evento = TransferRequestedEvent.builder()
                .transactionId(txId).fromAccount("ACC-001").toAccount("ACC-002")
                .amount(BigDecimal.ONE).timestamp(Instant.now()).build();

        // ACT — publicar el mismo evento DOS VECES (simula duplicado Kafka)
        kafkaTemplate.send("transfer.requested", evento.getFromAccount(), evento);
        kafkaTemplate.send("transfer.requested", evento.getFromAccount(), evento);

        // ASSERT — el producer solo publicó UNA vez (la segunda fue ignorada)
        await().atMost(10, SECONDS).untilAsserted(() ->
            then(producer).should(times(1)).publishValidated(any())
        );
        // Solo existe UN registro de idempotencia — no dos
        assertThat(processedEventRepo.findAll()).hasSize(1);
    }
}
⚠️
Gotcha con @EmbeddedKafka y @SpringBootTest: si tu clase de test no tiene @TestPropertySource redirigiendo bootstrap-servers al broker embebido, el consumer intentará conectarse a localhost:9092 (que no existe en CI) y el test fallará con timeout. Siempre incluye esa propiedad.

@SpyBean vs @MockBean: usa @SpyBean cuando quieres que el producer ejecute su código real (publicar en Kafka) pero también quieres verificar que fue llamado. Usa @MockBean cuando quieres reemplazar completamente el bean por un mock que no hace nada.

Para tests de consumers: @SpyBean ValidationEventProducer permite verificar qué se publicó en Kafka sin necesitar un consumer separado que lea esos mensajes.

MÓDULO 05 · CAPA 2B
Testcontainers
Kafka + MySQL reales

Testcontainers levanta contenedores Docker reales durante los tests y los destruye al terminar. La diferencia con @EmbeddedKafka: el Kafka y MySQL son idénticos a producción. Detecta bugs que @EmbeddedKafka no detecta: queries JPA mal escritas, problemas de charset, constraints de DB, serialización JSON real en el broker.

🐳
Kafka real
Usa KafkaContainer de Testcontainers. Versión idéntica a producción. Detecta problemas de serialización JSON que @EmbeddedKafka puede ignorar.
REAL
🗄️
MySQL real
Usa MySQLContainer. Flyway corre las migraciones. Detecta diferencias entre H2 (para tests) y MySQL real (charset, tipos, constraints).
REAL
♻️
Reuse de contenedores
Con .withReuse(true), el contenedor se reutiliza entre runs de tests (no se destruye y recrea cada vez). El primer test tarda ~10s, los siguientes <1s.
OPTIMIZACIÓN

Configuración base — AbstractIntegrationTest

JAVA · AbstractIntegrationTest.java 
/**
 * Clase base para todos los tests de integración.
 * Define una sola vez los contenedores compartidos entre todos los tests.
 * Extiende esta clase en lugar de repetir la configuración en cada test.
 */
@SpringBootTest
@Testcontainers
public abstract class AbstractIntegrationTest {

    // ── Kafka ──────────────────────────────────────────────────────────────
    @Container
    static final KafkaContainer KAFKA =
            new KafkaContainer(DockerImageName.parse("confluentinc/cp-kafka:7.6.0"))
                    .withReuse(true); // reutilizar entre runs → más rápido

    // ── MySQL ──────────────────────────────────────────────────────────────
    @Container
    static final MySQLContainer<?> MYSQL =
            new MySQLContainer<>("mysql:8.0")
                    .withDatabaseName("transfers_test")
                    .withUsername("test_user")
                    .withPassword("test_pass")
                    .withReuse(true);

    // ── Conectar Spring Boot a los contenedores ────────────────────────────
    @DynamicPropertySource
    static void kafkaProperties(DynamicPropertyRegistry registry) {
        // Sobrescribe los valores de application.yml con los del contenedor
        registry.add("spring.kafka.bootstrap-servers", KAFKA::getBootstrapServers);
        registry.add("spring.datasource.url", MYSQL::getJdbcUrl);
        registry.add("spring.datasource.username", MYSQL::getUsername);
        registry.add("spring.datasource.password", MYSQL::getPassword);
    }
}

// ── Uso en un test concreto ────────────────────────────────────────────────
class DebitConsumerIT extends AbstractIntegrationTest {

    @Autowired KafkaTemplate<String, Object> kafkaTemplate;
    @Autowired AccountRepository   accountRepository;

    @Test
    void debito_reduce_saldo_en_mysql_real() {
        var saldoInicial = accountRepository.findById("ACC-001").orElseThrow().getBalance();

        kafkaTemplate.send("transfer.validated", "ACC-001",
                TransferValidatedEvent.builder()
                        .transactionId(UUID.randomUUID().toString())
                        .fromAccount("ACC-001").toAccount("ACC-002")
                        .amount(BigDecimal.valueOf(150))
                        .timestamp(Instant.now()).build());

        await().atMost(15, SECONDS).untilAsserted(() -> {
            Account actual = accountRepository.findById("ACC-001").orElseThrow();
            assertThat(actual.getBalance())
                    .isEqualByComparingTo(saldoInicial.subtract(BigDecimal.valueOf(150)));
        });
    }
}

Trampa: @Testcontainers + @SpringBootTest = contexto de Spring para cada clase de test.

Si tienes 10 clases de test que extienden AbstractIntegrationTest y no usas .withReuse(true), Spring levanta y destruye el contexto 10 veces. Con reuse: el contenedor se levanta una vez, el contexto de Spring se cachea entre clases → los tests son 5x más rápidos.

Para que withReuse(true) funcione, debes crear el archivo ~/.testcontainers.properties con testcontainers.reuse.enable=true.

MÓDULO 06 · PATRONES AVANZADOS
Patrones específicos de
Kafka testing

Más allá de testear la lógica de negocio, hay comportamientos específicos de Kafka que debes verificar: que el ACK se confirma correctamente, que el sistema tolera mensajes malformados, que el rollback del Saga deja el sistema consistente.

Patrón 1 — Verificar idempotencia end-to-end

JAVA · IdempotencyIT.java 
@Test
@DisplayName("El mismo débito enviado 3 veces se aplica exactamente UNA vez")
void debito_idempotente() {
    String txId = UUID.randomUUID().toString();
    BigDecimal saldoInicial = getBalance("ACC-001");

    TransferValidatedEvent evento = buildValidatedEvent(txId, "ACC-001", "ACC-002", 100);

    // ACT — mismo evento 3 veces (simula at-least-once delivery de Kafka)
    for (int i = 0; i < 3; i++) {
        kafkaTemplate.send("transfer.validated", evento.getFromAccount(), evento);
    }

    // ASSERT — esperar que el primero se procese
    await().atMost(15, SECONDS).untilAsserted(() -> {
        // Saldo rebajado exactamente 100, no 300
        assertThat(getBalance("ACC-001"))
                .isEqualByComparingTo(saldoInicial.subtract(BigDecimal.valueOf(100)));

        // Solo UN registro de idempotencia — no tres
        assertThat(processedEventRepo
                .existsByEventKeyAndServiceName(txId + ":TRANSFER_VALIDATED", "account-service"))
                .isTrue();
        assertThat(processedEventRepo.findAll()).hasSize(1);
    });
}

Patrón 2 — Verificar compensación del Saga

JAVA · SagaRollbackIT.java 
@Test
@DisplayName("Cuando el crédito falla, el débito es compensado y el saldo queda igual")
void rollback_restaura_saldo() {
    // GIVEN — activar el flag de fallo de crédito en el contexto de test
    ReflectionTestUtils.setField(creditService, "simulateCreditFailure", true);

    BigDecimal saldoAntes = getBalance("ACC-001");
    String txId = UUID.randomUUID().toString();

    // WHEN — enviar el evento de débito (que desencadena el crédito fallido)
    kafkaTemplate.send("transfer.debited", "ACC-001",
            buildDebitedEvent(txId, "ACC-001", "ACC-002", 200));

    // ASSERT — esperar a que la compensación complete
    await().atMost(15, SECONDS).untilAsserted(() -> {
        // El saldo de origen quedó IGUAL que antes (compensación exitosa)
        assertThat(getBalance("ACC-001")).isEqualByComparingTo(saldoAntes);

        // Existe el registro de compensación en processed_events
        assertThat(processedEventRepo.existsByEventKeyAndServiceName(
                txId + ":COMPENSATION", "account-service")).isTrue();
    });

    // CLEANUP — restaurar el flag
    ReflectionTestUtils.setField(creditService, "simulateCreditFailure", false);
}

Patrón 3 — Verificar que el @Version previene doble débito

JAVA · OptimisticLockIT.java 
@Test
@DisplayName("Dos débitos concurrentes de la misma cuenta: solo uno tiene éxito")
void optimistic_lock_previene_double_debito() throws Exception {
    BigDecimal saldoInicial = getBalance("ACC-001"); // 1000.00

    // Lanzar 2 débitos simultáneos desde 2 threads
    ExecutorService executor = Executors.newFixedThreadPool(2);
    Future<?> t1 = executor.submit(() ->
            debitService.debit("ACC-001", BigDecimal.valueOf(600)));
    Future<?> t2 = executor.submit(() ->
            debitService.debit("ACC-001", BigDecimal.valueOf(600)));

    // Uno tiene éxito, el otro lanza OptimisticLockingFailureException
    AtomicInteger exitos = new AtomicInteger(0);
    AtomicInteger fallos  = new AtomicInteger(0);
    for (var future : List.of(t1, t2)) {
        try { future.get(); exitos.incrementAndGet(); }
        catch (ExecutionException e) { fallos.incrementAndGet(); }
    }

    assertThat(exitos.get()).isEqualTo(1);
    assertThat(fallos.get()).isEqualTo(1);

    // El saldo bajó exactamente 600, no 1200
    assertThat(getBalance("ACC-001"))
            .isEqualByComparingTo(saldoInicial.subtract(BigDecimal.valueOf(600)));
}

Los tests de concurrencia son los más difíciles de hacer bien. Un test que lanza 2 threads y verifica el resultado puede ser no determinístico si los threads no se sincronizan correctamente. Para este patrón, ExecutorService.submit() + future.get() garantiza que ambos threads iniciaron antes de verificar el resultado.

En producción real, pruebas de carga con Gatling o k6 serían más apropiadas para verificar comportamiento bajo concurrencia real. Pero para verificar que @Version funciona, este test es suficiente.
